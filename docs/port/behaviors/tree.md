# Behavior rules: Sidebar (folder tree, tree root, Favorites, Locations, volumes and eject, tree keyboard)

Prefix B-TREE. Improvements covered: A2, A16, A17.

What this area does better than Finder's sidebar, in code terms:

- Selecting a sidebar row IS navigation: every arrow, Home, End, Page, type-to-select step and click selects the row and opens its folder (history push), and the folder tree is a real expandable tree of the whole disk (lazy per-folder reads, expand and collapse from the keyboard, Alias folders never expand), not just a list of places.
- The tree has a movable top ("Use as Tree Root", Home, a disk, Macintosh HD) that re-roots itself when a folder outside it is opened, keeps hidden folders and packages visible only on the active path, and never lists other disks under Macintosh HD.
- Favorites are plain, user-ordered rows (drag to reorder, per-favorite icon, add and remove from any menu); Home, Macintosh HD, the Trash and mounted disks live under Locations with Finder's Eject button, the Eject/Force Eject questions and per-tab sidebar memory (scroll, open sections, selected row).
- A full keyboard model that Finder lacks: type-to-select with a 1000 ms reset, half and full page moves (Ctrl+U, Ctrl+D, Page Up, Page Down), Right/Left expand and collapse, and a sidebar-safe subset of file commands (copy, cut, paste into the folder, copy path, terminal).

Conventions. Evidence paths are relative to `apps/desktop/src/renderer/` in the original (`/Users/tcmudemirhan/src/tsproj/filetrail`, pinned `e4d0872`) unless they start with `main/` or `shared/` (siblings under `apps/desktop/src/`) or `packages/`. "Tree focus" means `focusedPane === "tree"`. "Row" means a sidebar row (a `.tree-row`): a heading, a favorite, a location or a filesystem folder. "Selected" means the tree selection id (`fs:<path>`, `favorite:<path>`, `location:<path>`), which is what the Swift port must keep as one value per tab. Numbers are ms or px. Test ids are from `docs/port/parity/tests.tsv` (matched by file and title); "-" means no original test checks the rule.

## Open questions

- Down arrow with nothing selected selects the second visible row (baseline index 0, then +1) while Up selects the first; this follows from the code and looks accidental. Port as coded unless told otherwise (hooks/useExplorerNavigationController.ts:1653-1700; also lib/treeView.ts:79-86).
- Clicking a filesystem folder that cannot be opened leaves the new row selected (the selection id is set before the folder opens) while the file list keeps the old folder and shows the error; the optimistic-selection test only covers the pane in isolation. Intended or a bug? (hooks/useExplorerNavigationController.ts:1440-1456, 1180-1215).
- lib/treeView.ts `getTreeKeyboardAction` and lib/typeahead.ts `findTreeTypeaheadMatch` are used by no production code, only by their tests (T-c3c420b1 T-eaf07a43 T-05d06d43 T-a5280d40 T-df5c84b6); the live behavior is in the controller (rules in sections 7-9). Decide whether those tests are ported or marked N/A.
- Type-to-select in the integrated layout can match the "Favorites" or "Locations" heading label and then select nothing, even when a folder row later in the list matches (for example typing "f" with a "Folder" row). Confirm this is acceptable.
- A selected-kind "favoritesRoot" exists in the shortcut policy (T-2c614522, T-709ce3da partly) but the heading can no longer be selected; treat as unreachable.
- The tree does not follow external file system changes except for the folder on screen (no watch on expanded branches); only write operations and tab re-entry refresh branches. Confirm the Swift port should not add watching.
- History: every tree-driven open uses push, including re-activating the row that is already the folder on screen; this code does not de-duplicate a repeated path (whether history de-duplicates is decided in the history area, nav.md).
- `Shift` with arrow, Home, End in the sidebar is accepted and acts as without Shift; Shift with Page keys is routed through the extend-selection handler which does nothing for the sidebar and still moves. Confirm.
- Eject availability while a file operation runs is not blocked in the original, though other write-starting commands are; confirm.
- The sidebar width range (220-520) and default (280) come from layoutTokens and the preference defaults; confirm the Swift split-view uses the same.
- In the separate layout a mouse press on a section header (Favorites or Locations) is handled as a press on empty space by the section's capture handler, so it clears the sidebar selection and empties the file list before the header's click toggles the section; the original tests only press the headings of the integrated layout (rows) or fire a bare click. Looks like a bug; the port copies it unless it is listed in DEVIATIONS.
- The unused helper tests (T-c3c420b1 T-eaf07a43 T-05d06d43 T-a5280d40 T-df5c84b6) are cited on rules where the production controller does the same thing; they prove the helper, not the app.
