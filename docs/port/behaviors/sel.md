# Selection, keyboard navigation, type-to-filter, inline rename, open and Return rules, marquee selection, paging (B-SEL)

Improvements it belongs to: A7, A9.

What File Trail does here that Finder does not, in code terms:
- Typing in the file list is a live filter (`lib/listFilter.ts`, `useExplorerNavigationController.ts:585-683`): substring match, selects the first name that starts with the text, a pill shows "n of total", Esc brings the whole list back and keeps the selection. Space belongs to the text for 1000 ms.
- The selection model keeps anchor, lead and a `gapIndex` (`lib/contentSelection.ts`): after items leave (Trash, delete, move) the arrow keys continue from where they stood; Back and Forward restore selection and scroll per folder (`lib/folderViewMemory.ts`).
- Paging (Page Up/Down, ⌃U/⌃D, rebindable, ⇧ extends) moves the selection by whole lines and scrolls only when the landing item is off screen, in all three views (`getPagedLineMove`, `handlePagedMove`).
- Marquee selection is computed from layout tokens, not the DOM, with ⇧ add and ⌘ flip modes, edge auto-scroll and a nearest-item lead (`lib/dragSelection.ts`, `hooks/useDragSelection.ts`).
- Inline rename survives scrolling, re-sorting and refusals: drafts are kept per rename session, an off-screen field keeps the keyboard, and refused names keep the field open (`InlineRenameField.tsx`).

Evidence paths are relative to `apps/desktop/src/renderer/` of the original (pinned at e4d0872); `../shared/` is `apps/desktop/src/shared/`. Test ids are from `docs/port/parity/tests.tsv`; "-" means no original test checks the rule.

## Open questions

1. Backspace in the filter: the comment on `eraseListFilterCharacter` says "the selection stays where it is", but `applyListFilter` re-selects (first name starting with the remaining text, else first match) whenever text remains. The rules above follow the code; a test for it is missing. Confirm with the reference app before porting.
2. Sorting, flipping folders-first and toggling hidden files go through `navigateTo` without `keepSelection`, so they clear the folder's selection (unlike refresh, which keeps it). The ContentPane reveal tests suggest the lead stays at the view level only. Confirm in the reference app that selection is really lost on sort.
3. A press on the list's scrollbar: the container's mouse-down handler calls `onClearSelection()` before `startDragSelection` rejects the press, so the selection looks cleared by a scrollbar press. Whether Chromium sends that mouse down to the container for a scrollbar is not covered by a test.
4. Window in the background: the code sets `window-inactive` on window blur (grey selection) and the pane's `onBlurCapture` sees a blur with no related target, so `focusedPane` becomes null; the restore effect then puts the keyboard back on the next render where no dialog is open. The exact order on a real window deactivate/activate is not tested; check in the reference app.
5. `contentEnter` is not in WRITE_STARTING_SHORTCUTS, so a held Return is not stopped from repeating the way a held F2 is. After the first Return the rename field has the keyboard, so the repeat is probably harmless; not tested.
6. Compact List (flow list) reveals only `selectionLeadPath` and has no off-screen rename field, unlike Details and Icon view. A rename starts on the selected item, so the lead is the renamed item, but a refused name does not bring it back into view in that view. Confirm.
7. ⌘. cancelling the inline rename field is handled only by the window's modal-cancel path (`isModalCancelKey`); no test covers it.
8. `handlePagedMove` returns false (key not consumed) when exactly one item is selected and the move lands on it; with several selected it collapses to that item. Only the "keeping one" half is tested.
9. Return with ⇧, ⌃ or ⌥ held is treated as Return by `contentEnter` (only ⌘ is excluded). Finder ignores or changes some of these; port as is unless told otherwise.
10. Typing in the content pane while a filter is active in search mode: the same `listFilterQuery` is shared by the results bar's filter field and the keys typed into the list. Edge cases of switching between them (caret, selection) are covered only by the search tests, not for the selection.
