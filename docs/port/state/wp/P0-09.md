## Goal

Finish the write-engine differential (PLAN.md §5.3) before phase 3 needs it. This closes phase-0 critic gaps 1–4. For a scenario, the reference engine records everything that matters, and a Swift-side runner contract lets P3 work packages check their engine against those recordings.

## You own

- `tools/parity/exec/`, `tools/parity/golden/exec-*.ts` and `tools/parity/golden/analysis-*.ts`.
- `Tests/FTTestSupport/Exec*.swift`.
- `Tests/Golden/exec-*.json` and `Tests/Golden/analysis-*.json`.

## Do

1. **Recorded outcome.** Extend `tools/parity/exec/run.ts`'s outcome so that, besides the before and after tree snapshots, it records:
   - the **ordered event stream**: progress, questions with their allowed answers, the answers given, and final statuses. Hidden staging paths are mapped to display paths, and timings and ids are normalized to ordinals;
   - the **undo log**, normalized (stop dropping it);
   - **Trash contents**: run each scenario with a scenario-local Trash, by pointing the engine's trash function at a temp folder the way the original's tests do, then snapshot it;
   - the **journal file** contents after each step that writes it.
2. **Stops and crashes.**
   - `stopAt: {afterEvent: n}` cancels the operation after the nth event, as the Stop button does.
   - `crashAt: {journalWrite: n}` kills the engine process right after its nth journal write. Run the engine in a child Bun process and `SIGKILL` it.
   - After a crash, run the reference's startup recovery on the same folder and record the outcome.
   - Find how the original's own tests do this (`packages/core/src/fs/*Recovery*.test.ts`, `apps/desktop/src/main/bootstrap/writeJournal.test.ts`) and reuse their seams.
3. **Analysis differential.** `tools/parity/golden/analysis-*.ts` generates seeded scenario trees covering:
   - file/file, folder/folder, type mismatch, package, symlink, case-only, into-itself, nested picks, locked and unreadable items;
   - cut vs copy, and same vs other volume where a disk image is available.

   It records the reference's analysis report (conflict tree, classes, issues, warnings, allowed choices), normalized, as `Tests/Golden/analysis-<suite>.json`. Aim for 150+ scenarios across the suites, mixing hand-picked cases from `docs/port/inventory/file-operations.md` §2 and §7 (checklists A and B) with random trees.
4. **Execution goldens.** Generate at least 40 execution scenarios into `Tests/Golden/exec-*.json`, covering: plain copy, merge, keep both, replace (file and folder), skip, cut on the same volume, a runtime conflict with each answer, stop mid-copy, and a crash at each journal step of a folder replace. Use the checklist in `file-operations.md` §7 (C–G and J) to pick them.
5. **Swift contract.** `FTTestSupport.ExecHarness` gives P3 tests:
   - build the scenario's `before` tree in a temp dir (or on a disk image when the scenario says so);
   - an `ExecEngine` protocol the Swift write engine will implement: `run(scenario, answers, stopAt, crashAt) async -> ExecOutcome`;
   - normalization identical to `run.ts`;
   - a comparator that reports the first differences compactly.

   Until the Swift engine exists, the tests run a `ReferenceReplayEngine` that returns the golden itself, proving the decode, normalize and compare path.
6. **README.** Update `tools/parity/README.md`.
