## Goal

The parity matrix (PLAN.md §5.2). It lists every test case of the original and every feature it has, so "done" can be counted rather than guessed.

## You own

- `tools/parity-matrix/` and `docs/port/parity/`.

## Do

1. **`tools/parity-matrix/extract.ts`** (run with `bun`) writes `docs/port/parity/tests.tsv` from the original at the pinned commit.
   - **Input.** Export the pinned tree read-only into a temp dir with `git -C /Users/tcmudemirhan/src/tsproj/filetrail archive e4d0872 | tar -x -C <tmp>`.
   - **Parsing.** Use the TypeScript compiler API, loaded from `/Users/tcmudemirhan/src/tsproj/filetrail/node_modules/typescript` (read-only), to walk every `*.test.ts`, `*.test.tsx` and `apps/desktop/e2e/*.spec.ts`. Collect each `it`/`test` call (including `.each`, `.skip`, `.only`, `.todo`, `.concurrent` and `.skipIf(...)`/`.runIf(...)` forms) together with its enclosing `describe` titles. Template-literal titles are kept as written.
   - **Columns.**

     | Column | Content |
     |---|---|
     | `id` | `T-` + first 8 hex of sha1(file + describe path + title), stable across runs |
     | `file` | The test file |
     | `describe` | The describe titles, joined with ` › ` |
     | `title` | The test title |
     | `form` | it, test, each, skip or todo |
     | `class` | L, FS, UI, E or e2e |
     | `area` | Short area name |
     | `swiftTarget` | Suggested Swift module |
     | `status` | `todo` |
     | `swiftTest` | Empty |
     | `note` | Empty |

   - **Class** comes from the per-file classification in `docs/port/inventory/app-shell-and-tests.md` §7. Use L for renderer `lib/*` files; files not listed there get a classification derived the same way (real temp dirs or disk images → FS, React rendering → UI, zod/ipc/preload/protocol → E).
   - **Merging.** Re-running the script keeps any `status`, `swiftTest` and `note` already filled in for an id (merge, don't overwrite). Rows whose id disappeared go to the bottom with status `gone`.
   - **Totals.** Print totals by class and by top-level area. The inventory counted about 3,366 cases (with `.each` tables counted once) plus 31 e2e. If your total differs by more than 3%, find out why and explain it in the summary.
2. **`tools/parity-matrix/report.ts`** prints a compact summary of `tests.tsv` by class and status, and a features summary by area and status. `state.py status-md` will later embed this output.
3. **`docs/port/parity/features.md`.** Write one table per area, with the columns `ID | Feature or behavior | Spec | Planned WP | Status`, built from the four inventories in `docs/port/inventory/`. Areas follow PLAN.md §7 (P1 to P6) plus "Cross-cutting".
   - **Rows.**
     - Every command, every preference, every dialog and menu, every view behavior, every file-operation rule and edge case (checklist A–N in `file-operations.md` §7), every system integration, and every layout and design rule in `ui.md`.
     - Specific enough that a test or a screenshot can prove each row. "Keep Both names a file `x copy 2` when `x copy` exists" is a good row; "naming works" is not.
     - Expect several hundred rows.
   - **Fields.** IDs are `F-001`, `F-002`, …. Spec cites `inventory-file §section`. Planned WP uses the WP ids of PLAN.md §7. Status is `todo`.
   - **Read the inventories section by section.** They are the source; don't re-derive from the TypeScript unless an inventory line is ambiguous.
