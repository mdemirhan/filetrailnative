## Do

1. **New steps**, implemented on both sides: the Swift automation runner and the Electron driver.
   - **`click {element, button?, count?, modifiers?}`**: by logical element name from `elements.json`, optionally with `{index}` or `{text}` to pick one of several (for example the row named "Avatar.jsx"). Swift synthesizes `NSEvent` mouse events at the element's frame center through `NSApp.sendEvent`, with no Accessibility permission needed.
   - **`menu {path: ["File", "New Folder"]}`**: Swift finds the `NSMenuItem` and performs its action. Electron triggers the same menu command.
   - **`contextMenu {element, choose: "Rename"}`**.
   - **`drag {from, to, modifiers?}`**: within the app and between windows. Swift synthesizes a mouse-down, drag and up sequence; if a native drag session can't be driven synthetically, call the drop handlers through a debug seam and say so in the report.
   - **`expectSheet {name}`, `sheetButton {label}`**: dialogs, alerts and sheets.
   - **`newWindow`, `newTab`, `selectTab {index}`, `selectWindow {index}`**.
   - **`fs {op: create|write|rename|delete|chmod|lock, path, …}`**: changes the fixture mid-scenario, for folder-watch flows.
   - **`expect {element, text?, visible?, count?}`**: a soft assertion recorded in the report.
2. **`prefs`.** Support every key of the original's preferences on the Electron side, since it seeds `app-state.json`. On the Swift side, keep a registry where later work packages register handlers for their preferences, so an unsupported key is reported per key without failing the run.
3. **Honest reports.**
   - **Missing elements.** An element present on one side and absent on the other is reported as `missing (swift)` or `missing (electron)`, separately from `off`. The runner line becomes, for example, `geometry: 2 off, 9 missing (swift)`.
   - **Selftest.** `--selftest` now also compares an Electron capture with itself and a hand-made pair of geometry dumps with a known 3 pt offset, which must be reported as off by 3 pt. That exercises the real comparison logic, not only identity.
4. **Scenario metadata.** Each scenario JSON gets `features: ["F-…"]` (rows it proves) and `tier: ["wp", "wave", "final"]`. `run.sh --tier X` runs the scenarios tagged with that tier. Tag the existing ten.
5. **More scenarios.** Add 10, Electron-side complete, that exercise the new steps:
   - context menu on a file;
   - rename via F2;
   - New Folder;
   - cut items, which shows the clipboard marks;
   - opening the clipboard popover;
   - Go to Folder (⌘K) with text typed;
   - the review sheet for a paste with a conflict;
   - a second tab;
   - Settings opened on the General tab;
   - an outside file created while the folder is shown.

   The Swift side may report unsupported steps for now.
6. **Acceptance flows** (PLAN.md §3.4a). Create `tools/capture/scenarios/acceptance/` with one Electron-complete scenario per improvement A1–A17, tagged `tier: ["wave", "final"]` and with the matching `features` ids. Write the scenario steps from the code-derived rules in `docs/port/behaviors/*.md` (the B- ids each improvement maps to), not from the table's one-line summary. Each flow lists the `B-` ids its steps check, under `behaviors`. The Swift side may report most steps unsupported for now. `run.sh --acceptance` runs only these.
7. **Docs.** Update `tools/capture/README.md`.
