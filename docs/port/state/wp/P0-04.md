## Goal

The differential harness of PLAN.md §5.3. The original TypeScript code produces the expected answers; the Swift tests must reproduce them. It works through **golden files**: Bun scripts run the reference's own functions and engine on seeded inputs and record the results as JSON in the Swift test targets. `swift test` then checks the Swift port against them without needing Bun. Re-running the generators in check mode detects drift when the reference is re-pinned.

## Do

1. **Loader (`tools/parity/lib/`).** Imports modules of the reference app by path from the reference build at `~/Library/Caches/filetrail-port/reference/electron`, so workspace imports (`@filetrail/contracts`, the `native-fs` addon) resolve through its own `node_modules`. Run Bun with the clone as the module root, or set it up so imports resolve the same way. Read the pinned commit from `docs/port/state/orchestrator.json`.
2. **Golden format.** Every golden lives in `Tests/Golden/<suite>.json`, a folder outside every target (so SwiftPM emits no unhandled-resource warning), and is located by path from the test's `#filePath`. The format is `{ "suite", "referenceCommit", "seed", "generator", "cases": [{ "name", "input", "output" }] }`, pretty-printed and with keys in stable order.
   - `tools/parity/gen.sh [suite...]` regenerates goldens.
   - `tools/parity/gen.sh --check` regenerates into a temp dir and fails with a compact diff if any committed golden would change.
   - Generators live in `tools/parity/golden/<suite>.ts`. Each one takes a seed, uses a small seeded PRNG shipped in `lib/`, mixes hand-picked edge cases with random cases, and exports the cases.
3. **`FTTestSupport`.**
   - `Golden.load(suite:in:)`, which decodes a golden file into `[GoldenCase<Input, Output>]` (generic and Codable).
   - A helper that compares and reports **only the first 10 mismatching cases**, each on one line: name, input, expected, actual.
   - A temp-directory fixture helper.
4. **Execution snapshots** (for the write engine later):
   - **`tools/parity/exec/snapshot.ts`** writes a normalized description of a directory tree: for every item, its relative path (NFD-normalized), kind (file, dir, symlink and its target), size, sha256 of contents, mode & 0o7777, BSD flags (uchg/hidden), and the presence of an ACL. Entries are sorted by path; timestamps and inode numbers are left out.
   - **`FTTestSupport.TreeSnapshot`** produces the identical JSON in Swift.
   - **`tools/parity/exec/selftest.sh`** builds a tree with every kind of item under a temp dir (reuse `~/Library/Caches/filetrail-port/fixtures/names` if it helps), snapshots it with both, and fails on any difference.
   - Stub `tools/parity/exec/run.ts`, which will run reference-engine scenarios (paste with a policy, answers to questions, stop points). Document its intended scenario JSON format in `tools/parity/README.md`, and make it run one real scenario through the reference's `packages/core` copy engine: copy one file into an empty folder. Record that scenario's before and after snapshots as `Tests/Golden/exec-copy-single.json`. The Swift engine doesn't exist yet; a test that only decodes the golden is enough.
5. **Worked example.** Port `withoutNestedPaths` and `isInsideTrash`/`isTrashFolder` from `packages/contracts/src/paths.ts` and `packages/contracts/src/trash.ts` into `Sources/FTFoundation/Paths.swift`. Give them golden suites `paths-nested` and `trash-paths`, with 300+ seeded cases each including NFD/NFC, case and `/Volumes` edge cases, plus Swift tests that pass. P1-01 will own and extend this file later.
6. **`tools/parity/README.md`.** How to add a suite, in under 40 lines.
