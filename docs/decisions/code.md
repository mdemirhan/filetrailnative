# Decisions: how the code is kept

How work lands, how it is tested and released, and what stays as it is in the code. Part of the owner's decisions: [the index](../decisions.md) lists the other parts.

- **Nothing is committed to `main` until the owner says so.** Work is done and committed in a worktree of its own (`.claude/worktrees/<name>`, on the branch `claude/<name>`), never in the main checkout, and stays on its branch until the owner says to land it. It then lands by fast-forward or rebase, never by a merge commit, and there are no pull requests. Changed on 2026-11-15: work used to land on local `main` as soon as it was done; the owner wants to look at it, and say when it goes in, first.
- **Nothing is pushed unless the owner asks.** Landing on `main` is local, and only when the owner says; pushing to GitHub is a step of its own.
- **A commit message is a short subject, then the rest in the body.** The subject says what is now true of the app in about 72 characters at most; after a blank line the body gives the detail, in as many plain sentences as it needs. No `Co-Authored-By` trailer. Changed on 2026-11-20: a message used to be one plain sentence, and those sentences grew to a median of 124 characters and as many as 1,171, so `git log --oneline` could not be read.
- **The commits are as many as the changes.** A fix or a feature is one commit, so each can be taken back or found by bisecting. Rewording of comments or docs goes in one commit for a module or an area, not one for each folder or file, and bookkeeping (an item of a plan ticked off) goes into the commit that did the work. A plan once landed in 401 commits, some 115 of them comments alone and 41 ticking items: too many to read.
- **`scripts/release.sh` runs the tests that drive real windows.** A release is run at the keyboard, and these are the only tests of real windows.
- **`scripts/ci.sh --affected` compares with the previous commit, not with `main`:** the last commit's files, uncommitted changes and new files. On a long branch every module differs from `main`, so it ran everything every time. With no commit before HEAD, or nothing changed, everything runs. The format lint follows the same files.
- **Hand checks are made by whoever does the work**, in the built app, driven by a scratch scenario ([tools/capture/README.md](../../tools/capture/README.md) says how). The owner checks by hand only when asked, and no longer asks for before and after pictures of a control change.
- **Goldens are expected results kept by hand.** A golden's expected outputs are edited by hand, never regenerated from the code's own output. Whoever makes a change updates the goldens it moves, without asking the owner (the owner, 2026-11-20; before, the owner was asked about any golden a task didn't name): each new expected value is checked against what the change should do, and one that doesn't follow from it is a bug to look into, not a value to write in. A golden is deleted only with the owner's yes. Six of them (shortcuts, command availability, preferences, the toolbar, right-click menus, Help) are written as bases and each case's changes to its base (`Tests/FTTestSupport/GoldenChanges.swift`), and are edited by hand in the bases and in the cases that differ. One exception: a new input field whose value follows from a case's other inputs may be added to every case by script, as `listShowsItems` was, from whether `entries` was empty. A golden file holds its bases and cases only, with no metadata fields. Changed on 2026-11-20: the bases-and-changes layout replaced whole outputs repeated in every case, where a new command touched every case, hundreds of the same hand edit. This entry was taken out with that change and is put back by the owner's ruling: the layout changed where an expected output is written, not that it is written by hand, and the exception for inputs is new.
- **The stop and crash recordings run through the write engine**, not only against themselves. All of them can; a recording that ever can't is deleted with the tests that only describe it. The shape tests of the recordings stay, each saying what it guards.
- **Tests that need a file that can't be written fail it with EIO**, not with a full disk, as a full disk now ends the paste.
- **The Undo types keep their hand-written `Codable`.** It is the journal's guard on its format.
- **The write engine's callbacks for Undo, caches and progress don't throw**, as nothing in the app throws from them.
- **The app installs its services once at launch, and the tests install theirs.** `ExplorerServices.current` has no fallbacks; the tests got faster without them.
- **Names with the earlier app's vocabulary were renamed only where plainly left over**: `RendererCommand` is `AppCommand`, `InfoLocale.original` is `InfoLocale.appLanguage`, `CSSTextMetrics.swift` is `TextLineMetrics.swift`, and the copy of `JSString.equals` went. `JSString`, `JSText` and `NodePath` keep their names: they name rules the app keeps, and renaming them is large. Others (`sortedJS`, `jsTrimmed`, `isJSWhitespace`, `jsLowercased`, `jsRound`, `nodeText`, `libuvWords`, `menuAccelerator`, `javaScriptNumber`, `PageWindow` and its kin) were not part of the answer and are left. Comments describe the app on its own terms, as `CLAUDE.md` says.
- **The Finder Trash workaround stays as a diff**, with the commit it applies to named in known-issues.md. That keeps the record at no cost.
- **A few benchmarks gate a release; none run in plain CI.** The one there is: the frame times of scrolling (`FrameTimeGUITests`, among the tests that drive real windows), which every release measures: the List, the Icons view and the Compact List, each at its default size and at its largest, on the fixture folder `large/files-3000`, each number the median of three scrolls. `scripts/release.sh` shows them against the last release made on the same Mac model and stops on a clear slowdown of a median or of the share of late frames (the slowest frame is shown and fails nothing); loose ceilings apply as well, and alone with no record from that model. Frame times that can't be read or compared stop the release. The limits, with the numbers measured beside them, are in `scripts/lib/frame-timing-limits.sh`. Anything else wanting speed is guarded by tests that bound CPU time (`CPUTime.measureThread`): no other benchmark tests, budgets or `--bench` modes. The fixture tree `large` holds the two folders the folder-size golden measures and the folder the frame times scroll.
- **A release goes one minor version up** unless the owner asks for a patch or a major one in words, even when all it holds is fixes.
- **Release notes are written for the people who use the app.** One point for each thing someone would notice, as many as the release holds, named as they would see it, with what it does for them in a sentence or two: "See what's running", "Folder sizes you can count on". Not a list of every change: small changes of one kind go into one point, and the rest are left out. How it works stays out: not the order things run in, how a list's rows behave, counts or limits, nor a name the app uses inside its code. Headings by area only where there are enough points to need them. Never a list of the commits, no list of known issues nor a link to one. The owner reads the notes before the release starts, as the tag keeps them. A release stays a draft until the owner says to publish it. Changed on 2026-11-17: the notes said what changed, area by area, and 1.4.0's first draft ran to twenty points of how sizes wait and how the Activity list's rows stay put; the owner found that unreadable, and its second, shorter pass a laundry list still.
- **Each release keeps its notes in its tag.** The notes are written for people before the release starts and given with `--notes <file>`; the script stops without them. The tag's message is "File Trail X.Y.Z", a blank line and the notes word for word (`--cleanup=verbatim`, so Markdown headings stay), and the draft release's text is the same file. A tag pushed to GitHub is never rewritten for this: notes changed on GitHub after the tag is made aren't in the tag. The releases before 1.0.0 had their notes put in their tags afterwards, and their GitHub releases were deleted; the tags stay.
- **Each release keeps its frame times in the commit it tags.** The release adds a record (the version, the date, the Mac model, macOS and the numbers) to `docs/frame-timings.json` in a commit of its own on the checked commit, holding that file alone, tags that commit, and pushes `main` with the tag at once (`git push --atomic`); a release that stops before the push takes both back. The frame times are shown again once the draft is made. A release run by an agent shows the owner that table, and publishes only with the owner's explicit yes.
- **A test run that matched no test fails**: `scripts/ci.sh --scope` and the release's tests of real windows (`scripts/lib/test-runs.sh`). A release refuses to run with `FILETRAIL_NO_DISK_IMAGES` set.
- **Tools nobody runs are deleted.** `scripts/hands-on-setup.sh`, the `FILETRAIL_TIMING` switch and `tools/acknowledgements` went. The licences the app shows are kept by hand in `Resources/Acknowledgements`. `--snapshot` stays: it draws a window into a PNG without screen-recording permission.
