# Decisions: Views and what they show

The List, Icons, Compact List and Previews views, their sizes, Quick Look, and how items are named and drawn. Part of the owner's decisions: [the index](../decisions.md) lists the other parts, and [principles.md](../principles.md) says how a decision is weighed and when to ask about one.

- **A folder's items, and search results, can be put in groups** (2026-11-20). View ▸ Group By, in every view: a folder by name, one of the four dates (Finder's relative groups, counted from midnight), size, kind or first tag; search results by any of these or by Folder (a first step had them group by name, folder and kind only). A group's title is in the system's secondary label color (2026-11-20), as Finder's, so a title is told from an item. The Previews label keeps the label's own color: it is on glass over the pictures, where the fainter color could not be shown to read over a dark one. The plan is [records/group-by.md](../records/group-by.md).
  - The groups keep a fixed order whatever the sort (newest dates and smallest sizes first, the rest A to Z) and the sort orders the items inside each, as in Finder. The sort's direction ordering the groups too, as first built, made no sense to the owner. Reverse Group Order turns the groups around, those without a value still last.
  - Groups don't collapse: chevrons, Collapse All and Expand All were built and taken out, the owner seeing no need.
  - Titles are the name alone, in Finder's layout with the app's own fonts.
  - The Compact List's groups follow one another down a column, each under its title over a hairline as wide as the column, and go on in the next column only when there is no room left; a column that goes on with a group starts with its title again, fainter, so every column names what it holds, and ← and → go to the item at the same height in the column beside. Until 2026-11-20 each group started a column of its own under a title held at the left edge; the owner found the columns disjointed.
  - In the List every group, the first too, has its title in a row of its own, and every title but the first has half a row above it; the Name column's title stays Name with its sort arrow. Changed on 2026-11-20: the first group's name stood in the column's title, which read as a column called "Today" or, in search results, "work", and an empty row before each title left about two rows between groups. The stripes start again under each title.
  - Search results' dates, sizes and tags are read a batch at a time, and the list is ordered and grouped again once when the read ends and at most once a second while it goes on. Values read stay while the same folder is searched and the field is needed, so another query reads only the results without one; the same search run again reads them again.
  - The grouping is the pane's, as its order is; a saved tab and a workspace keep it, and a folder's view can keep it as a sixth setting.
  - For search results a date, the size or the tags are read in the background, only that field and only while the results are ordered or grouped by it ("Nothing is read before it is needed").
- **The List has a Date Added column, and sorts by it** (2026-11-19). When each item was put in its folder, as Finder's Date Added: what Downloads is most often sorted by. Hidden until shown, as Date Created is, and sorted newest first. The folder read gives it with the other dates, so sorting by it costs nothing more. Disks that don't keep it (FAT, exFAT, most shares) leave it empty, and such items sort last. The Info panel doesn't show it, as Finder's Get Info doesn't.
- **The List has a Date Last Opened column, and sorts by it** (2026-11-19). What macOS records when a file is opened, as Finder's Date Last Opened; hidden until shown. It isn't in the folder read: it is read for the rows on screen, and for every item only while the folder is sorted by it, as sizes are. Items never opened show nothing and sort last. The home folder's Desktop, Documents and Downloads folders show none of their own, as reading them asks for permission (see Finder tags).
- **List view's columns keep the widths they were given.** A pane narrower than the columns scrolls sideways; no column shrinks or hides to fit, and Name is never squeezed. Widths change only when someone drags, steps or double-clicks a divider, so what is set is what shows.
  - A column narrowed with the list scrolled to its right end leaves empty room past the last column until the list is scrolled back, so nothing moves under the pointer. Before, the list scrolled back under the pointer and the column closed up to its smallest at once; closing the list up when the drag ended was tried and dropped, as the columns then moved at the release (2026-11-15).
  - The List's own scrolls go through the scroll view, not its clip view alone: macOS keeps its own record of where a trackpad left a list, and jumped back there the next time the width changed.
- **The Icons view's icon size and the Compact List's column width are set with one slider in the status bar**, and with View ▸ Make Bigger, Make Smaller and Default Size (⌘+, ⌘- and ⌘0; ⌘= is ⌘+'s other key, as most keyboards type + with Shift). Icons go from 32 to 128 pt, columns from 160 to 600 pt; the List has none. Dragging the gaps between columns was tried and dropped: nothing on screen shows the gaps can be dragged. An Icons item's column is its icon plus 40 pt, never below 80: smaller icons fit more items across, and a name still has a 78 pt label for its two lines. Holding the column at 104 pt below 64 pt icons was what there was, and only made the rows shorter; no floor would leave a name 70 pt.
- **Each pane has its own sizes.** Decided 2026-11-15. The icon size, the Compact List's column width, the Previews count and the List's column widths (a folder's and search results' apart) belong to the pane, at each density, as its view and order do, and are saved with it in a saved tab and a workspace. The size set last in any pane is the app's: a pane with none of its own starts from it, and a pane opened from another takes that pane's. One size for the whole app was what there was: a workspace could not bring its sizes back, and a size set for one folder's photos changed every other pane. Column widths were the window's, from before there were panes: a Name column widened for one folder widened it in the other pane and every tab. Panes saved before start from the app's sizes and their window's widths.
- **A folder can keep its own view** (2026-11-19). View ▸ Folder View ▸ Remember View for This Folder keeps six settings: the view, the order, Folders First, the List's columns, the size and the grouping. A pane still carries its own settings from folder to folder; a folder's view is laid over them while the pane shows that folder, and leaving puts back what the pane carried, so a photo folder kept in Previews doesn't bring Previews into Downloads. A setting the folder's view doesn't keep follows the pane. Hidden files stay the tab's, and search results keep their own view. Considered and dropped: a default view for every other folder, as Finder's Use as Defaults (it would end the pane carrying its settings); remembering every folder visited, as Finder does (a quick look in Icons would change a folder for good); hidden files per folder.
- **Folder View Options chooses what a folder's view keeps, and saves what is changed** (2026-11-19). One popover (⌘J, Finder's key for View Options; also from the menus and the status bar's symbol) with a Keep checkbox and a control for each setting, Apply to Subfolders, Reset, All Folder Views…, Revert and Save. What is changed in it is a change on screen as any other: it shows at once, Save keeps it, Revert or leaving the folder drops it. With every box unchecked and Apply to Subfolders off, Save removes the folder's view.
  - It replaced two popovers, options that saved each change at once and Unsaved Changes with Update and Revert: the owner asked why there were two for the same settings, and two rules for saving.
  - Reset waits for Save too. It removed the customization at once at first; the owner wanted it to wait as everything else in the popover does. View ▸ Folder View ▸ Reset Folder View still removes at once, as Remember saves at once: those commands are the saving.
  - In a folder that uses a view from above, the popover says whose the settings are, with a Go to button to that folder; Save gives this folder a view of its own, and Apply to Subfolders starts off. Saving to the folder above from below, and a Customize This Folder button, were there first: the owner found two ways to save from a subfolder unclear, as Go to already leads there.
  - There are always four setting rows and the buttons are dimmed rather than removed, so the popover keeps its height and its buttons don't come and go. A changed row has an orange dot whose tooltip says what is saved. No control has the keyboard as it opens.
  - Each checkbox is titled with its setting's name, so a click on the name checks it, as on any Mac; Folders First is a pop-up, as a switch said little either way. An earlier layout (a subtitle saying whose view it was, a slider, arrows, a switch, grey cards, controls stretched to one width) was dropped: the owner found the words unclear and the look cheap.
- **A folder's view is saved only when asked** (2026-11-19). In a folder with a view, a change of view, sort, Folders First, column or size changes only what is on screen; Update Folder View (Save in Folder View Options) saves it, Revert to Saved View drops it, and leaving the folder drops it without a question. Only Remember, Save and View ▸ Folder View ▸ Reset Folder View save: a Keep box, Apply to Subfolders, the popover's Reset and Keep Columns for … are changes on screen. A setting changed back by hand is no change, and a setting the view doesn't keep is the pane's. The owner chose this over saving each change as it was made, which made every quick look a lasting change and left the subfolder question to be guessed at every change. A question on leaving was not considered: it would add a step to the commonest thing done.
- **A pane or tab opened from another shows a customized folder's saved view** (2026-11-20). Duplicate Pane, Duplicate Tab and Reopen Closed Tab show the folder's view as it is saved, not changes that were on screen and unsaved in the pane they come from: a change is kept only with Save, and is dropped whenever the folder is left.
- **A setting a folder starts to keep is given back to the pane** (2026-11-19). What is changed in a folder before it is customized is the pane's, and would be carried to every folder after it. So the pane notes what it carried in, and once the folder keeps a setting the pane goes back to its noted value of it; a setting the folder doesn't keep stays as the pane has it. Before, the first Remember left the pane with the folder's view in every folder after: the owner found that annoying. Of the app's columns and sizes, the pane puts back only what it changed itself in that folder, and only where it is still as the pane left it. Putting all of them back as they were hid a column shown from another tab since (the owner's choice, 2026-11-20).
- **A folder's view can cover the folders inside it, and the nearest view wins whole** (2026-11-19). With Apply to Subfolders, every folder below without a view of its own uses it. A folder uses one view only, its own or the nearest covering one above, never settings from several. Settings looked up one at a time across levels was drawn first and dropped: a folder could take its view from one folder and its order from another, and nothing on screen could say why.
  - A view that keeps nothing and covers the folders inside is how a branch stops using a view from above. Apply to Subfolders with nothing kept is a change only where it does that; anywhere else the switch is dimmed, as it lit Save and made a customization that changed nothing (2026-11-20).
  - Save in a folder that uses a view from above gives that folder its own view; the folder above is changed in it, by Go to. Update first asked which, and the folder above's options listed the folders inside with their own view: the owner had both dropped as more than the case needs. Folder Views lists those folders instead.
- **A folder's view shows as a symbol at the right end of the status bar** (2026-11-19). In every folder, left of the size slider: accent when the folder has its own view, the label's color when it comes from a folder above, grey when it has none, with an orange dot while something is unsaved; the symbol is 13.5 pt in its 18 pt place. It was 12 pt, grey from above and faint with none: faint, the way to the options in most folders was easy to miss, so none became grey, and from above a step stronger so the two still differ (2026-11-20). A click opens Folder View Options, and the menus and ⌘J open it from the symbol.
- **The Info panel shows the file's own picture** (2026-11-20). Where Quick Look has a preview (a photo, a PDF's first page) the panel's large icon is that preview, in its own proportions; the icon shows until it comes and stays for a file with none, for folders and for several items. It is read for the one item shown, from the Icons view's store, so a picture already on screen there is drawn at once. The List's rows and the Info Row keep the icon.
  - It was first shown only where a folder had a view; the owner had it always there, as the symbol is a way to the options in any folder, and a popover opened from the menu otherwise rose from the item count. It keeps its place whether or not the view has a slider, so an open popover doesn't move.
  - A pill with words was drawn first and dropped: it took 130 to 190 pt from the path beside it.
  - Search results, and a pane that let go of its folder, have none, and Folder View Options closes with it: left open, its Keep boxes changed the view of a folder not on screen (2026-11-20).
- **The Folder View commands are a submenu of View, of the list's right-click menu and of the toolbar's View Options menu** (2026-11-19). The same submenu in all three; an item's right-click menu has none, as "this folder" would be ambiguous there. A headed section in the View Options menu was tried and dropped: no other part of that menu has a heading. The names are whole ("Update Folder View") as the palette, Help and Settings show them alone. The toolbar button is in Customize Toolbar only.
  - Manage Folder Views… opens a window of its own, Folder Views, that lists every customized folder as a tree, a folder customized inside another under it. It was first a list in Settings → Browsing; the owner wanted it apart from Settings.
  - Remove forgets the selected folders' customizations; Remove with Subfolders those of every folder inside them too. Neither asks, as each says what it does; Remove All… asks. The owner wanted a choice about the folders inside.
  - A row is one line, the path with tags of what it keeps. A plain table of paths was built first (cheap, flat, no Esc), then rows of two lines under an explanation (needlessly tall, the explanation needless, a selected row's tags unreadable, "Folder Views" the wrong name).
- **The List's columns are chosen on its header** (2026-11-19). A right-click on a column title checks the columns shown, moves the one clicked left or right, sizes all to fit and resets them; a title dragged sideways moves its column; Name is always on and first. View ▸ Columns has the same items. An Edit Columns popover and a button at the header's end were drawn and dropped: the header's own menu is where a Mac list keeps its columns, and a button there would scroll away. Settings → Browsing no longer has the column checklists.
  - A change goes to every folder without columns of its own, or to the folder's view, unsaved until Save; the menu says which. Keep Columns for "…" makes them the folder's own, and in a folder using a view from above gives it a view of its own (before, it did nothing there; the owner's choice, 2026-11-20).
  - Search results have the same menu without the Keep item, and a title dragged there moves the results' own column: it had moved the folder List's (2026-11-20).
- **Fields and columns are listed in one order** (2026-11-19): Name, Date Modified, Date Created, Date Last Opened, Date Added, Size, Kind, Permissions (search results put Folder after Name), in every menu, the palette, Settings and Help. It is the order of Finder's column header menu. Sort By had Finder's order for that menu, which differs; the owner wanted the same order everywhere. A column shown takes its standard place among those shown; one moved by hand stays there, but hidden and shown again it comes back in its standard place, as remembering a hidden column's place would need a record of which were moved by hand. Date Created sorts too, newest first: the owner found it missing from Sort By.
- **Folders' views are kept in `folder-views.json`, and a folder's view is found by its full path only** (2026-11-19; by the path alone since 2026-11-20). In Application Support, with nothing written into the folders, so views work on disks and shares that can't be written. Finding a folder's view is a look in memory, with no call to the disk.
  - It replaced a view found by its disk, its canonical path and the folder's file ID, which found a folder again after a rename or move in Finder but made opening a folder resolve its path and read its ID on the main thread: the owner decided a folder customization should not need any additional lookups. Old files load, and their `volume` and `fileID` are dropped at the next write.
  - Accepted with this: a folder renamed or moved outside File Trail loses its view and stays in Folder Views as Not Found; a folder at the same path on another disk of the same name uses the same view. Views are never removed on their own (kept as it is, 2026-11-20).
  - A rename or move made in File Trail, and its Undo, take the folder's view and every view below it along. Only then is the new place resolved to its real path, once, so a folder dropped on a link doesn't save its view under the link's path. One operation's views are all taken before any is put back, so a batch rename that swaps names leaves each folder its own (2026-11-20).
  - A folder reached through a link shows the view saved for its real path, which its listing gives; it is read once more only where that view's order differs.
  - A view's parts are read one by one, a missing one taking its default, so a column added to the app costs no folder its columns. A file that can't be read is renamed to `folder-views.json.unreadable` just before it would be written over, so nothing in it is lost; before, the next save wrote over it (the owner's choice, 2026-11-20).
  - Dropped: `app-state.json` (written with every tab and window change), SQLite (more than a few hundred entries need), an extended attribute on each folder (writes into the folders and fails on many disks and shares).
- **A size step and the selection.** A new icon size or column width keeps the item at the top left of the view (the Icons view) or the column at its left (the Compact List) in place. The selection's lead stays in view if it was in view just before the step; one out of view is left there, and later layouts don't bring it back until it is shown again. (No reason recorded.)
- **A folder opened afresh in the List starts at its top and its left**, an empty one too; Back and Forward put back where it was scrolled. A rename with Name scrolled out of view scrolls back to the left first. (No reason recorded.)
- **Previews is the fourth view.** View ▸ as Previews (⌘4) shows a pane's files as large Quick Look previews in a grid that scrolls down, 9, 4 (the default), 2 or 1 at a time, set by the slider and Make Bigger and Make Smaller; the count is the pane's own. Everything else is the Icons view's: selection, keys, drags, rename, every command.
  - View ▸ Show Previews has 9, 4, 2 and 1 at a Time, each switching to Previews at that count from any view, with the selected file brought on screen, as the commands are for showing that file at a size. A submenu, as the View menu is long already; menu items and not keys in Settings alone, so the menu shows the key chosen and the count on screen. Pressed again an item changes nothing, rather than going back to the view before, so its key and checkmark mean one thing.
  - The toolbar's Previews segment shows the same four on a press held, as Back and Forward's do. The system's arrow was tried and dropped: it made the segment wider than the others, and a click on it didn't open the menu.
  - The places share the pane's width and height exactly, so a row shows whole and nothing of the next; a scroll settles on a whole row. Each picture keeps its own proportions, never stretched.
  - At 1 at a time the file a scroll rests on is selected, so Space, the Info panel and Move to Trash act on the file on screen; a selection of several, one made by a drag, or one being renamed is kept. Before, the selection stayed on a file no longer shown (2026-11-18). At 2, 4 and 9 scrolling leaves the selection alone, as in Icons: moving it would put Move to Trash on a file never picked.
  - For the same reason (2026-11-20): arriving at 1 at a time by Show Previews selects the file shown unless several are selected; when the selected file is removed, the one that takes its place is selected; and a view put back at 1 at a time with one file selected shows that file, not the place saved, which in a pane of another height is another file's row. A held ⌘⌫ still trashes one file, as a held key repeats no command that starts a write.
  - Previews are asked of Quick Look at their place's size, again only once a resize has rested a quarter of a second; a picture too large for Quick Look (about 3.5 million pixels) is read by the app, two at most at once. The pages after and before the one on screen load ahead. A place stays empty a fifth of a second before the icon shows, so a quick preview isn't drawn over an icon.
  - Their cache is apart from the Icons view's: at most 1 GB or a sixteenth of the Mac's memory, least recently used first, 8 bits a color, all dropped when macOS says memory is short. Quick Look's own disk cache is left alone.
  - Considered and dropped: a triage mode with single-letter keys and an Apply step, kind chips in the filter, Trash Others on Page, retake groups, copying an image or its text, renaming from the text in a picture, and live previews. A magnifier while ⌥ was held was built and removed: it showed little the preview at full size doesn't.
- **The View Mode Menu is the view switch in one button**, for a toolbar short of room (decided 2026-11-17): 36 pt where the four-segment switch is about 136. It is in the default toolbar (see the default toolbar in windows-and-panes.md) and the switch stays in Customize Toolbar; both can be in a toolbar at once. It shows the symbol of the view on screen, and its menu has the four views and the Previews counts, so nothing the switch does is lost. Considered: a switch that folds itself into the button when the toolbar is short, as Finder's does; the owner asked for a second item to choose instead.
- **A file can be shown in a pane: Open in Viewer in place, Open in Other Pane beside the list** (2026-11-20). The plan is [plans/text-viewer.md](../plans/text-viewer.md); the mocks are on the design canvas "File Trail Text Viewer", boards 10 and 11 for this design. What was decided:
  - **Two ways in, and nothing else in the menu bar.** File ▸ Open in Viewer (⌘E), and a file's right-click menu after Open With, for one file. Open in Other Pane (⌥⌘↓, and ⌥⌘E) takes a file as well as a folder: the file shows in the other pane's viewer, which follows the list. ⌘E was Eject's and ⇧⌘E Edit in Text Editor's: both have no default key now (the owner, 2026-11-20). An earlier design with View File (F3), a Viewer Pane toggle (⇧F3), Follow Selection, Next and Previous File, Edit Text and Save in the menus was built and dropped: dimmed items in the menu bar, and a toggle that could disagree with Two Panes.
  - **What the viewer does is in the viewer**: its bar shows what applies now (Read or Edit, Save while there are edits, Follow beside the list, the next and previous file in place), and its ⋯ menu the rest, with the keys the viewer takes while it has the keyboard (⌘S, ⌘F, ⌥⌘] and ⌥⌘[, Esc). Save File, Next File and Previous File can be given other keys in Settings → Shortcuts, under Viewer (the owner, 2026-11-20).
  - **A file shown in place is a step of the pane's Back and Forward.** Back returns to its folder with the file selected; Forward shows it again.
  - **While a pane shows a file, what acts on its folder or its items is dimmed**: views, sorting, groups, filters, the file commands. Acting on the file shown would act out of sight (the owner, 2026-11-20).
  - **A viewer beside the list is the second pane**: Two Panes closes it and brings it back as it was; ⌘W closes the file first, then the pane.
  - **Following goes on while editing**: a new selection asks Save, Don't Save or Cancel when there are edits, and Cancel puts the selection back on the edited file. Follow turned off keeps one file.
  - **Read or Edit is remembered** for the next file, and with each pane in a workspace.
  - **A file opens to Read or Edit as chosen last; Save is ⌘S**, written beside the file and put in its place so it keeps its permissions, tags and dates. Leaving a file with edits asks: Back, another file, closing the viewer, the pane, the tab or the window, and quitting.
  - **The keyboard goes into the text when its pane is focused** (a click, Tab, Focus Content Pane). In Read, the arrows, Space, Home and End move the text rather than a caret, and Tab goes on to the next pane as from a list; the app's page and half-page keys move it in Read and in Edit. **Esc in Edit goes to Read and Return in Read goes to Edit**, keeping the keyboard, for that file only (the Read and Edit switch is what a next file opens in); **Esc in Read closes the viewer, in place and beside the list: the pane shows its folder again**, keeping the keyboard, and the panes stay as they are (the owner, 2026-11-20: one rule in both, as a different one beside the list confused. Closing the viewer's pane with it, as Close Pane would, was tried and taken back: Esc took away more than the file. Before that, Esc beside the list gave the keyboard back to the list, then did nothing there, and for a while it did nothing in place either, which the owner took back). The viewer has the keyboard for a file that isn't text as well (a picture, Quick Look's preview, a message), so Esc and Tab reach it. **⌘S saves only in the pane that shows the file** (the owner, 2026-11-20). **A click anywhere in the viewer makes its pane the active one** and gives the viewer the keyboard, on Quick Look's preview and the bar too, which take none of their own (the owner, 2026-11-20). **What would act on the folder under a file the pane shows waits**, as it would happen out of sight: its commands, and the toolbar's search field while the active pane shows a file (the owner, 2026-11-20).
  - **The pane's bottom bar tells of the file**, its line, language and format, in place of the folder's path: the folder isn't on screen, and a path bar there went to folders out of sight. The Go menu's places wait while a pane shows a file, for the same reason; Back, Forward and Enclosing Folder go to its folder first.
  - **Edited is the text against the file**: Undo back to the saved text leaves nothing to save.
  - **Space stays Quick Look.**
  - **The viewer's appearance and theme are its own, one for the app, in its ⋯ menu.** Settings has no page for them: the General page keeps to the app's theme and accent.
  - **Highlighting is the app's own lexer, a line at a time with a state carried between lines; no dependency.** Tree-sitter waits for the owner's yes once its size is measured.
  - **Markdown's Preview shows the pictures on the disk, never one on the web** (the owner, 2026-11-21). A relative path is read from the file's folder; the picture is drawn at its pixels as points, as a browser shows it, shrunk to fit the pane and never enlarged. An HTML `<img>`, as READMEs write one to size or center a picture, is drawn the same way at its `width` and `height`, centered by `align="center"`, with the tags around it left out (the owner, 2026-11-21, on this project's README). A picture that starts a list item has the bullet at its top. One on the web shows as its description: fetching it tells whoever serves it that the file was read (a tracking pixel), and the viewer reads nothing from the network. The pictures are read with the file, off the main thread, and one added in Edit once the Preview shows it; at most 2048 pixels on a side and 256 MB of them for one file, so a file of many photos can't take gigabytes. Before, every picture showed as its description.
  - Not yet confirmed by the owner, as built: the limits (shown and editable to 50 MB, colored to 10 MB) and the six built-in themes.
- **Quick Look is ⌘Y and Space**, as in Finder. ⌘Y comes first, so the File menu and Help show it (the menu can't show Space) and the toolbar's tooltip names it.
- **With hidden files shown, Quick Look's button and the hidden-files button both show an eye.** Kept as is. (No reason recorded.)
- **The folders drawn by the system are the real special folders, by path:** the startup disk's `/Applications`, `/Developer`, `/Library`, `/System` and `/Users`, and the home folder's Applications, Desktop, Documents, Downloads, Library, Movies, Music, Pictures and Public. A folder of one of these names elsewhere is an ordinary folder, tag color and all. (No reason recorded.)
- **Listings and naming use one list of 37 package extensions.** `.rtfd`, `.xcworkspace`, `.photoslibrary`, `.pkg`, `.sparsebundle`, `.key` and the rest show as one item, not a folder, and carry the system's kind ("Keynote Presentation"). Before, listings knew 10 and called the others folders.
- **The startup disk is shown by its real name**, as other disks already were, so a renamed startup disk is no longer called "Macintosh HD"; open windows and the Go menu's item follow a rename. Help and the startup disk's row in Settings' Shortcuts keep "Macintosh HD": they name a command, as Go ▸ Home does, and the Shortcuts label also feeds Help's golden.
