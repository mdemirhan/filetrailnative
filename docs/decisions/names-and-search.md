# Decisions: Names, search and filters

How names are ordered and matched, what search and the filters find, and the Go To, Move To and Extract To box. Part of the owner's decisions: [the index](../decisions.md) lists the other parts, and [principles.md](../principles.md) says how a decision is weighed and when to ask about one.

- **Names sort one way everywhere, in the user's language, with numbers in order.** One order (ICU's collator for the user's locale, numeric, ignoring case and accents) serves the folder listing, the tree, path suggestions, search results, Open With and volumes, so `file2` comes before `file10` in search results as in a folder, and a Swedish or Turkish user gets their alphabet's order, as in Finder. For an English user only search results changed. Kind labels and extensions compare as words, digit by digit. The locale is read once at launch. Without the system's collator, names compare as text through Foundation; no table of our own is kept for that case, as it would happen only if macOS dropped `libicucore` for everyone at once.
- **Names the language holds equal come in a fixed order.** `a.ts` and `A.ts`, `Résumé.pdf` and `résumé.pdf`, `file1` and `file01` compare equal in the user's language; they are then ordered by their text, byte by byte (`NameOrder.compareText`), in folders, the tree and search results, whatever order the disk gave them. A descending sort reverses it with the rest. `listing-sort.json` and `search-sort.json` were edited by hand to match, each case checked to differ only by tied names.
- **Accents match one way, however a name is stored.** Wherever a name is matched against what is typed (the list filter, the search results' filter, Plain Text search, the sidebar's type-to-select and Go To), a plain letter finds the letter with or without an accent ("e" finds e, é, è, ê and ë) and a letter typed with its accent finds only that letter, whether the disk keeps it composed or decomposed. Only Latin, Greek and Cyrillic letters lose their accents; a letter that isn't an accent on another (ø, ł, ı) stays its own. In scripts whose marks don't compose with their letter (a Devanagari or Thai vowel sign, a Hebrew point, an Arabic vowel) the letter typed alone finds it under any marks, and typed with marks finds it with those marks only. Case folds as Unicode folds it where that gives one letter ("ſ" is "s"), "ß" stays "ß". A ligature is found by its letters ("fi" finds "ﬁ", which is marked whole) and a full-width letter or digit by the plain one. One matcher (`NameMatcher`) holds the rule. A stored name is never changed, and marks fall on the name as stored. Everywhere else paths compare byte for byte (see [must-stay.md](must-stay.md)).
- **Typing finds names by their letters in order.** In a folder, a name is kept when it has the letters typed in that order (Fuzzy), with no rule about where words start; Contains keeps the letters side by side. Fuzzy is the default. The mode belongs to the view: a folder's list in its pane, and a search's results. A view takes the mode last chosen anywhere when it opens (a pane, a tab, a window, the results of a new search), and after that only Fuzzy and Contains in its own bar (the chip in the search results' field) change it, for the filter typed and the ones typed next; the same choice is what views opened later start with. No other view changes with it, nor any filter already typed: a pane keeps its mode from folder to folder, results already open keep theirs through a new query, results put away and brought back (Done, Back, Forward, Show Last Search Results) keep their filter's text, mode, selection and scroll, and the folder comes back from results in the mode it had. A pane is saved with its folder's mode, as with its view and its sizes: it comes back in it at the next launch, from a workspace, by Reopen Closed Tab and Duplicate Tab, and in a tab moved to another window, whatever was chosen last elsewhere (2026-11-15; until then the mode was saved nowhere, and every pane brought back started in the mode chosen last anywhere). A pane saved before that, and the pane of a new tab or a new window, start with the mode chosen last; the mode of a search's results is not saved, as the results aren't. There is no setting for it: Settings → Browsing's "Typing filters by" was removed, as it only did what the bar does, and changing it changed every view showing no filter, including one that wasn't being looked at. Until then an empty filter showed that one setting, so switching in one pane switched every other pane with nothing typed. Decided 2026-11-15. Over search results the name follows the same setting and the folder a result is in is always matched as Contains, as letters scattered over a path would match nearly every result. The letters matched are marked; over search results a filter's marks replace the search's while it is typed. The selection goes to the first name starting with the text, then the first containing it, then the name the letters fit best. An item selected by hand that the other mode, or unpinning, comes to hide leaves the selection, so no key acts on an item out of sight. A filter that only grew looks only through what it kept, unless a key changed a letter typed before (a mark after "ạ" makes "ậ", which "ạ" doesn't find): then it looks through everything.
- **Plain Text search finds what the filters find.** fd gets a regular expression that ignores case and finds every accented and decomposed form of each plain letter, and each character of any script however a name spells it: decomposed, partly composed or with its marks in another order ("が" stored as "か" and its mark, a Hangul syllable as its jamo, "ậ" as "ạ" and a circumflex), and a character the matcher reads as another (a compatibility ideograph, the Kelvin sign) (`PlainTextPattern`), for every Plain Text query, digits included: measured on a home folder of 738,221 items, it costs fd no more time than `--fixed-strings`. The expression is made of the text's first 64 characters, as fd refuses one that compiles to more than 10 MB, which some 500 characters came to; a name that holds the whole text holds its start, and the matcher judges the whole. The app's matcher then judges each result before it counts, so a search and a filter typed over the same names agree; a test runs the bundled fd over such names and compares what it hands over with the filter. Plain Text ignores case always; Glob and Regex keep fd's smart case and compare names as stored. There is no fuzzy search through fd: letters in order over a disk find tens of thousands of names and would need a best-match order and a limit of their own.
- **Search stops at 50,000 results.** Fixed, with no setting. A keystroke of the filter over 50,000 results took about 18 ms on an M4 Max once names were compared byte by byte or folded once.
- **A regular expression gets 5 ms of the main thread per name while search results are marked.** One that takes longer stops marking any more names for that search; the search itself is fd's and goes on.
- **A filter can be pinned to its pane.** View ▸ Pin Filter, or the pin in the filter bar, pins the filter typed in a folder; the same item, checked while pinned, or the pin again, unpins it, and the text is an ordinary typed filter again, to edit or clear. The bar's ✕ removes the filter, pinned or not. A pinned filter belongs to its pane, not the tab or a folder: it applies to every folder the pane goes to and to its search results until it is unpinned or removed, and the other pane keeps its own or none. While pinned it applies to files only, so folders always show and the pane can still be walked; a typed filter still filters folders too. It is locked: typing selects the first name that starts with what was typed (as the sidebar's type-to-select, a pause starting over, nothing shown), Backspace and ⌥⌫ do nothing, Esc lets go of the letters only, and the mode it was pinned with stays: the other can't be chosen. Showing or renaming an item it hides (Reveal, Go To a file, a paste) unpins it, and a toast says so. ⌘F does not carry it into the search field. It moves with its pane through Swap Panes, and is carried where a typed filter is: by Duplicate Tab, for the pane whose view the tab keeps. A tab moved to a new window or merged into another leaves it behind, as it leaves its typed filter, its history and its search; Reopen Closed Tab, New Tab and New Window start without one, and nothing of it is saved when the app quits. Pin Filter has no default key. The pin leans 45°. A pin per folder, a second filter typed on top of the pinned one, and saving a pinned filter to the Favorites were each tried in mock-ups and dropped.
- **The filter is a bar across the foot of the list.** While a filter is typed or pinned, a bar 30 pt tall lies under the list, as wide as the pane, opaque and washed with the accent: the filter symbol, the text, "12 of 45", then Fuzzy and Contains as a segmented control, the pin and the ✕. The list ends above it, so no item is under it, and it goes with the filter. Text that matches nothing turns it red. The modes take only clicks, as the pin and ✕ do, so typing stays in the list. A press anywhere on the bar, its buttons included, gives the keyboard to the list above it, so in a tab of two panes the pane becomes the active one, as a press on its list, its search bar or its Trash bar makes it; until 2026-11-15 the bar swallowed the press, and its buttons changed the filter of a pane that stayed inactive. It replaced (2026-11-15) a glass pill floating over the foot of the list, which covered the items under it, with a chip that switched the mode; the bar's room let both modes show at once. A find bar with a field and Done, the path bar turning into the filter, and the filter as a token in the path bar were tried in mock-ups and dropped.
- **Space and the filter.** Space never starts a filter. While one is typed, Space types a space for a second after each key and then is Quick Look; taken off Quick Look in Settings, it always types a space. The arrows always move the selection; the filter has no caret. ⌥⌫ takes the filter's last word back.
- **Go To, Move To and Extract To are one box with two purposes.** They share the field, the completions, the ranking and the keys; what differs is what the box is for. Go To (⌘K, ⇧⌘G) opens empty with the best place selected, so Return goes there, and a click on a row goes there at once: going somewhere is quick and Back undoes it. Move To and Extract To choose where items go: they open on the folder shown, as "~/…/Folder/" and all selected, so the folders inside it are listed, typing a name replaces it, and Return sends the items there (Move says when they are all in it already); nothing in the list is selected before something is typed, a click only puts a folder in the field, the pointer over a row selects nothing (in Go To it does), and a double click or Return sends them where the field says. Their list is the opened folders and favorites with the folders chosen before in Move To and Extract To (kept in `destination-folders.json`, scored as visits picked in Go To are), and the other pane's folder first. A folder typed that doesn't exist yet, in one that does, is made on the way after a second Return: the button says Create and Move (or Extract) and the line under the field says so; it is a New Folder of its own, undone apart from the move, and none is made inside an item being moved or in the Trash. In every box ↑ and ↓ put the selected folder's path in the field, from "~" and ending in "/", and leave the list as typed until something is typed, which goes on from that path; Esc gives back what was typed, and a second Esc closes the box. Tab puts the selected folder (or a path's first completion) in the field and lists the folders inside it, so it moves the focus only when there is nothing to complete; ⇧Tab always moves it. "./", "../", "." and ".." are paths from the folder on screen. Two separate boxes were weighed and dropped: the fixes to the field would have been made twice.
- **The search results' bar keeps its filter at least 200 pt wide; with less room the scopes are one pop-up.** The scopes ("Search:", the folder searched, Home, the disk) are segments while they fit beside a filter of 200 pt, and the filter gives up its width, from 280, before they do. With less room, as in a pane of two on a laptop's screen or a narrow window, they are one pop-up button naming the place searched, as wide as that name needs rather than its longest place, its menu each place with its icon, and the filter takes the rest of the bar. The filter keeps its 200 pt there too: where the place's name would leave it less, the name is cut short with an ellipsis, down to a button of 72 pt (its icon, a few letters and its arrows), and only in a bar with room for neither, as in a pane of two at its narrowest, does the filter give up more, to about 120 pt in a pane of 280. Until 2026-11-15 the pop-up took the width its name needed first, and in such a pane a place named with a dozen letters left the filter 2 pt wide; "Search:" goes, as the button names a place and its accessibility label says what it is. The button is a plain button of the pane as the segments are: a click leaves the keyboard with the results, only Tab stops on it (where the filter's Shift-Tab and the toolbar's Tab land), Space or Return opens the menu, and no arrow changes the scope while it is closed. The keyboard on one form moves to the other when the bar changes form. Before, the segments kept their width and the filter shrank to 150, and in two panes the segments were cut off ("Home", "M…"). The results' filter has no icon at any width: its mode chip and its placeholder say what it is. An icon that went first when room ran short and came back beside the pop-up was mocked up and dropped as too fussy, as were the filter on a second row under the scopes, the scope beside the result count in the status bar, and the filter folded into a button over the scopes. Decided 2026-11-15.
- **A folder found takes a drop; the rest of the search results don't.** A drag onto a folder among the results goes into it, whatever the drag came from: Finder or another app, the other pane, or the results themselves (moving what was found into a folder found). The same rules as anywhere decide copy or move and refuse a folder into itself, an item onto itself or into the folder it is in, and an alias or a folder in the Trash. The results' background and their files take nothing, since the results come from many folders and have none of their own; a drop there into the folder searched would put the items where they may not show again. Resting on a folder doesn't open it, as that would leave the search. What a drop does to the results is in "Search results change only where a write acted on them". Until then only a drag from another app was taken, and File Trail's own drags were refused on the same folders, with no reason kept for it. Decided 2026-11-15.
- **Search results change only where a write acted on them, and are never searched again by it.** A write acts on a search's results when one of its items is a result, or it put items into a folder found; it is a write started in the tab on screen, or a move dragged out to another app. Then what it moved to the Trash, deleted, or moved into another folder leaves them, with every result inside it; what it renamed in its own folder keeps its row and its selection under the new name, though the search would no longer find it, with every result inside a renamed folder following, and a result renamed together with the folder it is in following that folder under its own new name; the row is then shown as any row is, so text typed since the search began that narrowed the results, or a filter typed or pinned over them, hides it when the new name no longer matches (decided 2026-11-15: a row going away there is right, as what is on screen is what matches the text in the field); and when it put something inside the folder searched (a copy, a drop on a folder found, a result moved into one, a Replace), nothing is added: a banner over the results says "Items added since this search may not be listed." with Search Again. A search still running when a write changes its results says so too, as it may yet give what the write changed; results it kept from the search before and finds again are still listed once, where they were or under their new names. The banner goes when the search runs again (Search Again, ⌘R, another scope, a new search) or is cleared, and comes back with results put away and shown again. Results put away (Done, Esc, opening a folder) change as shown ones do. A write that touches no result and goes into no folder found leaves the results as they are, though it changes the folder searched; so do Empty Trash, an Undo or Put Back none of whose items is a result (an Undo of a rename renames the result back), and writes in other tabs and windows. Nothing watches the folders searched: what Finder and other apps change shows once the search runs again. Until then every write that changed something in the tab on screen ran every search shown there again in full, emptying the list first, in both panes. Adding what arrived to the results without searching, by searching only what arrived, by matching it in the app, or by keeping rows at moved items' new paths, was each weighed and dropped: the rules of `fd` (hidden folders, ignore files, full-path matching) can't be told apart from the outside, and the cases where a guess goes wrong outnumber those it saves. A watch on the folder searched, to say the results may be stale after a change from another app, was dropped as too broad: a search of Home or the disk sees every change on the Mac. Decided 2026-11-15.
- **A search's options are its own, and a search opened later starts with those chosen last.** Match (Name, Full Path), Match As, Search Subfolders, Skip .git Folders and Skip Files Ignored by Git are chosen in the search field's menu for the search of the pane it drives; the choice is also saved, that option alone, and every search opened later starts with it: another pane's, another tab's, another window's, in this launch or the next. No search already open changes with it. The order of results is kept the same way, by its column. There is no Settings page for them: Settings → Search, which set what new windows started with and changed the tab on screen with it, was removed, as it repeated the field's menu and changed a view that wasn't being looked at; its Columns in Search Results moved to Settings → Browsing, after Columns in List View, as the only place they are chosen. Until then a new tab copied the options of the search on screen in its window and a new window took those of Settings, so the same choice carried in one window and not in another. Decided 2026-11-15.
