# Decisions: Names, search and filters

How names are ordered and matched, what search and the filters find, and the Go To, Move To and Extract To box. Part of the owner's decisions: [the index](../decisions.md) lists the other parts, and [principles.md](../principles.md) says how a decision is weighed and when to ask about one.

- **Names sort one way everywhere, in the user's language, with numbers in order.** One order (ICU's collator for the user's locale, numeric, ignoring case and accents, read once at launch) serves the folder listing, the tree, path suggestions, search results, Open With and volumes, so `file2` comes before `file10` in search results as in a folder, and a Swedish or Turkish user gets their alphabet's order, as in Finder. Kind labels and extensions compare as words, digit by digit. Without the system's collator, names compare as text through Foundation; no table of our own is kept for that case, as it would happen only if macOS dropped `libicucore` for everyone at once.
- **Names the language holds equal come in a fixed order.** `a.ts` and `A.ts`, `Résumé.pdf` and `résumé.pdf`, `file1` and `file01` compare equal in the user's language; they are then ordered by their text, byte by byte, in folders, the tree and search results, whatever order the disk gave them. A descending sort reverses it with the rest. `listing-sort.json` and `search-sort.json` were edited by hand to match, each case checked to differ only by tied names.
- **Accents match one way, however a name is stored.** Wherever a name is matched against what is typed (the filters, Plain Text search, the sidebar's type-to-select, Go To), a plain letter finds the letter with or without an accent and a letter typed with its accent finds only that letter, whether the disk keeps it composed or decomposed. One matcher (`NameMatcher`) holds the rule; a stored name is never changed. Everywhere else paths compare byte for byte (see [must-stay.md](must-stay.md)).
  - Only Latin, Greek and Cyrillic letters lose their accents; a letter that isn't an accent on another (ø, ł, ı) stays its own. In scripts whose marks don't compose with their letter, the letter alone finds it under any marks, and typed with marks finds those marks only.
  - Case folds as Unicode folds it where that gives one letter ("ſ" is "s"); "ß" stays "ß". A ligature is found by its letters and a full-width letter or digit by the plain one.
- **Typing finds names by their letters in order.** In a folder, Fuzzy keeps a name that has the letters typed in that order, with no rule about where words start; Contains keeps the letters side by side. Fuzzy is the default.
  - The mode belongs to the view, a pane's folder list or a search's results (decided 2026-11-15). A view opens in the mode chosen last anywhere, and after that only its own bar changes it; no other view changes with it, nor any filter already typed. Until then an empty filter showed one setting, so switching in one pane switched every other pane with nothing typed.
  - There is no setting for it: Settings → Browsing's "Typing filters by" was removed, as it only did what the bar does and changed views that weren't being looked at.
  - A pane is saved with its folder's mode, as with its view and sizes (2026-11-15; until then every pane brought back started in the mode chosen last). The mode of a search's results is not saved, as the results aren't.
  - Over search results the folder a result is in is always matched as Contains, as letters scattered over a path would match nearly every result.
  - The selection goes to the first name starting with the text, then the first containing it, then the best fit. An item selected by hand that the filter comes to hide leaves the selection, so no key acts on an item out of sight.
  - A filter that only grew looks only through what it kept, unless a key changed a letter typed before (a mark after "ạ" makes "ậ"): then it looks through everything.
- **Plain Text search finds what the filters find.** fd gets a regular expression that ignores case and finds every accented, decomposed or differently composed form of each character, for every Plain Text query: on a home folder of 738,221 items it costs fd no more time than `--fixed-strings`. The app's matcher then judges each result, so a search and a filter typed over the same names agree; a test compares the two over the bundled fd.
  - The expression is made of the text's first 64 characters, as fd refuses one that compiles to more than 10 MB, which some 500 characters came to; the matcher judges the whole text.
  - Plain Text always ignores case; Glob and Regex keep fd's smart case and compare names as stored.
  - There is no fuzzy search through fd: letters in order over a disk find tens of thousands of names and would need a best-match order and a limit of their own.
- **Search stops at 50,000 results.** Fixed, with no setting. A keystroke of the filter over 50,000 results took about 18 ms on an M4 Max once names were compared byte by byte or folded once.
- **A regular expression gets 5 ms of the main thread per name while search results are marked.** One that takes longer stops marking any more names for that search; the search itself is fd's and goes on. (No reason recorded.)
- **A filter can be pinned to its pane.** View ▸ Pin Filter, or the pin in the filter bar, pins the filter typed; it belongs to its pane, not the tab or a folder, and applies to every folder the pane goes to and to its search results until it is unpinned or removed. A pin per folder, a second filter typed on top of the pinned one, and saving a pinned filter to the Favorites were each tried in mock-ups and dropped.
  - While pinned it applies to files only, so folders always show and the pane can still be walked.
  - It is locked: typing selects by first letters, as the sidebar's type-to-select, Backspace does nothing, and the mode can't be changed. Unpinned, the text is an ordinary typed filter again.
  - Showing or renaming an item it hides (Reveal, Go To a file, a paste) unpins it, and a toast says so.
  - It is carried where a typed filter is (Swap Panes, Duplicate Tab) and left behind where one is (a tab moved or merged, Reopen Closed Tab, New Tab, New Window). ⌘F doesn't carry it into the search field, and nothing of it is saved at quit. Pin Filter has no default key.
- **The filter is a bar across the foot of the list.** While a filter is typed or pinned, an opaque bar 30 pt tall lies under the list: the text, the count, Fuzzy and Contains as a segmented control, the pin and the ✕. The list ends above it, so no item is under it. It replaced (2026-11-15) a glass pill floating over the foot of the list, which covered items and had a chip that switched the mode; the bar's room lets both modes show at once. A find bar with a field and Done, the path bar turning into the filter, and the filter as a token in the path bar were tried in mock-ups and dropped.
  - Its controls take only clicks, so typing stays in the list. A press anywhere on it makes its pane the active one; until 2026-11-15 the bar swallowed the press, and its buttons changed the filter of a pane that stayed inactive.
  - Text that matches nothing turns it red.
- **Space and the filter.** Space never starts a filter. While one is typed, Space types a space for a second after each key and then is Quick Look; taken off Quick Look in Settings, it always types a space. The arrows always move the selection; the filter has no caret. ⌥⌫ takes the filter's last word back. (No reason recorded.)
- **Go To, Move To and Extract To are one box with two purposes.** They share the field, the completions, the ranking and the keys. Two separate boxes were weighed and dropped: the fixes to the field would have been made twice.
  - Go To (⌘K, ⇧⌘G) opens empty with the best place selected, and Return or a click on a row goes there at once: going somewhere is quick and Back undoes it.
  - Move To and Extract To choose where items go, so they open on the folder shown with nothing in the list selected; a click only puts a folder in the field, the pointer over a row selects nothing, and Return or a double click sends the items where the field says. Their list adds the folders chosen there before and puts the other pane's folder first.
  - A folder typed that doesn't exist yet, in one that does, is made after a second Return, the button saying Create and Move (or Extract). It is a New Folder of its own, undone apart from the move, and none is made inside an item being moved or in the Trash.
  - ↑ and ↓ put the selected folder's path in the field; Esc gives back what was typed, and a second Esc closes the box. Tab completes, and moves the focus only when there is nothing to complete; ⇧Tab always moves it. "./" and "../" are paths from the folder on screen.
- **The search results' bar keeps its filter at least 200 pt wide; with less room the scopes are one pop-up.** Decided 2026-11-15. The scopes (the folder searched, Home, the disk) are segments while they fit beside a filter of 200 pt, the filter giving up its width from 280 first; with less room they are one pop-up button naming the place searched. Before, the segments kept their width, the filter shrank to 150, and in two panes the segments were cut off.
  - The pop-up is as wide as its name needs, cut short down to 72 pt so the filter keeps its 200; only a bar with room for neither takes the filter lower (about 90 pt in a pane of 280). Until 2026-11-15 the pop-up took its width first, and could leave the filter 2 pt wide. Since 2026-11-17 the filter beside it stops at 280 pt and no longer grows as the window narrows.
  - The segments have no "Search:" before them and no quotes, and are at most 160 pt: the toolbar's title already says what is searched. Until 2026-11-20 those took about 65 pt and a segment could be 220, so the pop-up came in panes the segments now fit.
  - The pop-up is a plain button of the pane, as the segments are: a click leaves the keyboard with the results, and no arrow changes the scope while it is closed.
  - The results' filter has no icon: its mode chip and placeholder say what it is. An icon that went first when room ran short was mocked up and dropped as too fussy, as were the filter on a second row, the scope in the status bar, and the filter folded into a button.
- **A folder found takes a drop; the rest of the search results don't.** Decided 2026-11-15. A drag onto a folder among the results goes into it, whatever it came from (another app, the other pane, the results themselves), by the same rules as anywhere. The results' background and files take nothing: the results come from many folders, and a drop into the folder searched would put the items where they may not show again. Resting on a folder doesn't open it, as that would leave the search. Until then only a drag from another app was taken and File Trail's own were refused, with no reason kept for it.
- **Search results change only where a write acted on them, and are never searched again by it.** Decided 2026-11-15. A write started in the tab on screen (or a move dragged out to another app) acts on the results when one of its items is a result or it put items into a folder found. Until then every write in the tab ran every search shown there again in full, emptying the list first.
  - What it trashed, deleted or moved to another folder leaves the results, with every result inside it. What it renamed keeps its row and selection under the new name, though the search would no longer find it; text typed since, or a filter, still hides a row whose new name doesn't match, as what is on screen is what matches the text in the field.
  - What it put inside the folder searched is not added: a banner says "Items added since this search may not be listed." with Search Again. Adding it by searching only what arrived, matching it in the app, or keeping rows at new paths was weighed and dropped: the rules of `fd` (hidden folders, ignore files, full-path matching) can't be told apart from the outside, and the cases where a guess goes wrong outnumber those it saves.
  - A search still running when a write changes its results shows the banner too. Results put away change as shown ones do.
  - Writes that touch no result, writes in other tabs and windows, and Empty Trash leave the results alone. Nothing watches the folders searched: a watch was dropped as too broad, as a search of Home or the disk sees every change on the Mac.
- **The search options can be found from the results as well as from the magnifier, and show when one has been changed.** Decided 2026-11-17. The magnifier's small chevron was easy to miss, and with it every option. The results bar has an Options button that opens the same menu: one button, not the options as segments, so the filter keeps its room.
  - It gives up its title, to its symbol alone, before the filter gives up any of its 200 pt and before the scopes become their pop-up (since 2026-11-20: three places to search in were judged worth more than the word).
  - While any option differs from a new install's, a dot in the accent sits on Options, and on the field's magnifier while the field has the keyboard, and their tooltips name what differs. A dot on the field at rest was tried and read as noise.
  - Considered: the options as segments (they took the filter's room), a chip in the field (it took the field's room), the placeholder naming them (gone once typing starts), and a tip shown once (it nags and helps once).
- **The toolbar's search field folds to its magnifier when the toolbar is short of room, and Compact Search is the field folded until it is used.** Decided 2026-11-17. Once the title is down to its least width the field folds to a magnifier, before any other item goes to the » menu, and opens again when there is room for it and 12 pt more, so a window at the edge doesn't open and fold it in turn. In use (the keyboard, text, or results in its pane) it is open whatever the room. Until then it never folded: at 900 pt four items went to the » menu while the field kept its 200.
  - Compact Search, in Customize Toolbar, is the same field folded until it is used. A toolbar holds one of the two, as there is one field. Considered: Finder's one item that decides for itself; the owner asked for two to choose from.
  - The toolbar holds the search item as the field or as a plain magnifier button, and swaps one for the other in place; the saved order names the item, never its form. The owner chose the plain button after trying it against the system's round magnifier around a stand-in field, which looked like Finder's but brought items back from the » menu about 60 pt late and needed its presses and dimmed drawing redone.
  - Also tried and dropped: holding the system's own field folded with width constraints (it gave the field the keyboard back about 200 ms after Esc, so Esc had to be pressed twice), and hiding an item for a moment to make the toolbar lay out again (it flickered, and set off the same refocus).
  - With items in the » menu, the room they leave stays before the » button: that is the toolbar's doing, and a title that asks for that room sends every item to the » menu.
- **Customize Toolbar offers the items in groups, as the menus group them.** Going about, the title, how the folder is shown, the search field, the panes and panels, opening the selection, changing files, the clipboard, undoing, where items are, the app, and the space last, where the system puts its own. The items every toolbar holds are in their groups too. Until 2026-11-17 the order had grown item by item, with the space first and the items every toolbar holds at the end.
- **A search's options are its own, and a search opened later starts with those chosen last.** Decided 2026-11-15. Match, Match As, Search Subfolders, Skip .git Folders and Skip Files Ignored by Git are chosen in the search field's menu for the search of the pane it drives; each choice is also saved, and every search opened later starts with it. No search already open changes with it. The order of results is kept the same way. Until then a new tab copied the options of the search on screen and a new window took those of Settings, so the same choice carried in one window and not in another.
  - There is no Settings page for them: Settings → Search was removed, as it repeated the field's menu and changed a view that wasn't being looked at. Its Columns in Search Results moved to Settings → Browsing.
