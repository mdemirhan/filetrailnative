# Decisions: File operations and the clipboard

Copy, move and Replace, what protects files while they run, folder sizes, and Paste as File, Copy Contents, Share and Convert Images. Part of the owner's decisions: [the index](../decisions.md) lists the other parts, and [principles.md](../principles.md) says how a decision is weighed and when to ask about one.

- **A full disk ends a paste.** The first "no space" error stops the run, the rest is "Not started", and a partly copied folder is not put in place. There is no free-space check before a paste starts, for now: that is a feature of its own.
- **A file moved to another disk goes even if the disk refused an extended attribute.** A refused attribute is skipped on purpose (most files carry `com.apple.provenance`, and FAT and exFAT refuse many); only a resource fork that can't be written fails the copy. An attribute that fails for lack of room or over a disk error (`ENOSPC`, `EDQUOT`, `EIO`) is not refused, and fails the copy as well (2026-11-20): on a full FAT or exFAT disk the "._name" file that holds a file's attributes can't be made, and skipped there, an empty file moved with its tags and comments lost its original and them with it.
- **A move to another disk is written out to that disk before the original is deleted.** Copied, an item may be only in memory or in the drive's own cache; deleted then, a power cut leaves it nowhere. Files moved one by one, and those of a folder merged into one that is there, are copied first and written out once at the end of the paste, however it ends, one flush for each disk they went to (`sync_volume_np`, some 30 ms); their originals go only then, each after the same checks, so a crash part way leaves files in both places and loses none. A folder is written out once, whole, when it is in place. A file put in place of another is still flushed on its own (`F_FULLFSYNC`). Changed on 2026-11-20: each file was flushed as it was copied, 4 ms against the 0.07 ms a small one takes to copy, to guard a power cut in that moment. A disk that can't be told to flush (some network disks) is left to itself, and a copy that fails to be written out keeps its original and says so. While the copies are written out and the originals removed, the progress card says "Finishing…" where the bytes were, and the Activity list "Finishing" where the percent was (2026-11-20): every item is counted by then, a slow stick can take long over it, and Stop no longer stops it, so the card sat at 100% with no word. The paste says so once, before the first flush, and only when it has such originals to remove. Before, the original went once the copy had the same kind and size.
- **A folder that goes whole or not at all stops at its first failed item** (2026-11-20). A folder moved to another disk, and a Replace's new folder, copy nothing more once an item failed: the hidden copy is cleared away either way, and the result names that item. Before, the rest was copied and then thrown away, a 200 GB folder for one file too large for the disk. A plain copy goes on and is put in place with its failures named. Whole or not at all stays, as a folder left half on each disk is harder to follow and to undo.
- **The journal entry that guards a moved item's only copy is flushed to disk.** Other journal entries aren't, for speed; this one is written once per Replace.
- **A folder moved to another disk keeps its journal entry until the originals are gone.** After a crash in between, recovery says what was left of the original and where.
- **A rename of several items is of one disk** (the owner, 2026-11-20). Items on more than one disk are not renamed together. The Rename sheet says so as soon as it has checked the items, in its footer ("These items are on more than one disk. Rename them one disk at a time."), with Rename off and Return doing nothing; the new names still show. The rename itself refuses with the same words whatever asked for it, before anything is moved aside, written down for recovery or kept for Undo. Why: the journal entry that guards a rename, for the items moved aside under hidden names while others take theirs, records one disk, and after a crash that disk is what tells an item whose disk is away from one that is done with. With items of several disks in one entry that could not be told for the others, and an entry could be kept for good. A disk for each item would have changed the journal's format; the owner chose to refuse instead, as such a rename only comes from search results that span disks. What else holds:
  - An item is on the disk of the folder it is in, a link to that folder followed, so a link or a mounted disk among the items counts as where its name is. A folder that can't be read counts for no disk, and its items fail for their own reason.
  - The sheet judges every item it was opened on, also those the settings would leave unchanged, as it says so before any setting is typed; the rename judges the items it is asked to rename.
  - Several folders of one disk are renamed together as before.
  - Recovery takes an entry written before this as it did: such an entry may hold items of several disks, and its items are kept only while another disk is where the first item's folder was. The journal's format is unchanged.
- **An operation that can't be undone stays in the Undo history, and what was done before it can still be undone** (2026-11-20). A move to another disk, a merge, a copy to a disk without a Trash, Empty Trash: each is kept where it happened, with what it was and why it can't be undone, and the Undo History list shows it there, dimmed, with a lock. Undo that meets one undoes nothing and says so in a toast, once; the next Undo takes the operation before it, as stepping past it silently would undo something the person didn't mean. Until then Edit ▸ Undo reads "Can't Undo" and stays on. Once passed, the entry is listed above the list's "Undo" heading, under a heading of its own, "Can't Be Undone", so the Undo heading sits over what Undo takes next and the entry isn't read as one of Redo's dimmed rows. An operation undone past such an entry must find the very item it acted on, not another of the same name and kind, and is refused otherwise: the operation in between may have put another item there. Operations done after every such entry, and Redo, still take an item of the same kind under the same name, for a document another app saved by replacing its file; an item with no id (FAT, exFAT) goes by kind, as there is nothing else to go by. This replaces the rule that such an operation emptied the history, which made an ordinary move to a USB stick cost every earlier Undo.
- **Progress counts are taken back when a Replace is undone or asked again**, so the count done never passes the total.
- **A conflict question takes one answer.** If the answer can't be sent, the question stays, its buttons disabled, and Escape still dismisses it.
- **A Replace row in the paste review says what goes to the Trash**, as its footer does, not "Deletes".
- **A disk mounted in a folder is never replaced** (2026-11-20). A folder on another disk than the folder holding it is where a disk is mounted: a share at `~/mnt/server`, a disk image at a mount point of its own. The paste review doesn't offer Replace for it ("Can't replace: It is a disk mounted here."), and the paste refuses it again when it gets there, before the pasted item is moved aside or anything goes to the Trash, as the disk may have been mounted since the review; the pasted item stays where it was. Replacing it would put the whole disk in the Trash, or, where there is no Trash and "delete for good" was agreed to, delete every file on it: the delete stops at a disk mounted inside the folder it started on, and here it would start on the disk itself. It costs the paste one look at the holding folder for each folder replaced (the review has read it already), and nothing for a file, as a disk is only ever mounted on a folder. Merging into such a folder is as it was. A folder that only holds one, further in, is still offered, as the Trash takes it with the disk still mounted inside. Where there is no Trash and "delete for good" was agreed to, it is refused with nothing deleted and the pasted item left where it was (2026-11-20): "“2024/share” is another disk, mounted inside “Album”, so “Album” wasn't deleted for good and nothing was replaced. Eject it and try again." The delete stops at such a disk, so the folder was left half deleted with nothing put in its place. The disk is found by the look for locked items that every delete for good makes first, after the question: a look of its own before the question would walk each such folder twice, so in this rare case the person answers the question and is then told why nothing was done. The review counts the folder a disk is mounted on as one item of the folder that holds it, and neither its counts nor the paste's look inside go into that disk; only a pasted folder of the same name is still compared with it, as merging into it needs.
- **A copy is checked for its source's whole resource fork.** A copy that reports success with less of the fork than its source fails (`ft_check_resource_fork`): with ENOSPC when the destination's disk hasn't the room for the fork, EIO otherwise, and the caller removes it as any failed copy. copyfile was once seen to report success with no fork at all on a full disk; why was not found (16 full runs didn't bring it back). One way to it was found and closed (2026-11-15): a copy that copyfile ended in failure without setting errno was told as done, and now fails as the fork's check says; whether that was what had been seen was not shown, so the check stays whatever the cause.
- **What a later try of leftover work finds is told as at start.** A move found in place, a rename put back, a folder put in place: shown under "Work was cut short when File Trail last stopped", before the items now in place, in a dialog of their own. Each message is told once, counting what the start already said, so an entry whose record can't be removed doesn't repeat itself every minute.
- **Calculating a folder's size is best effort** (2026-11-17). What can't be measured inside the folder is left out and the size of the rest is shown: a sub-folder gone, replaced, renamed or without permission to read, one reached only through a folder swapped for a link (it would be outside the folder measured), and a listing broken part way by a read error. A measurement fails only when the folder itself can't be measured. The size is approximate anyway (changes made outside the app leave it as measured), and failing gave no size at all, most often in `~` and `~/Library`, where apps add and delete files all the time. The code keeps whether each size is complete or partial, and why, with nothing shown for now, so something can be done with it later. This replaces the rule that a sub-folder replaced, or gone with the folder it was listed in, or a listing broken part way, failed the walk as incomplete.
- **A folder size asked for is never stopped by another request** (2026-11-16). Calculate Size on a second folder, by any route, waits for the first instead of stopping it: both were asked for, and Finder measures both. Only Stop, closing the window or quitting end it early; a write by the app under it lets it finish: the folders that hold the change, the one asked for among them, are given their size but not kept, and are measured again when next asked for (2026-11-20: it used to run again from the start, throwing away minutes of walking for one rename, while a change from outside was taken as approximate). Asking again for a folder being measured or waiting, Recalculate included, joins that measurement, whose answer is as fresh as a new one's (2026-11-17: this line said Recalculate ended it early, against the plan and the code). At most 10 asked requests wait, for the whole app, a run of several folders counting as one; past that the oldest waiting one is dropped, never the one running, so a burst of requests doesn't keep the Mac walking long after they stopped mattering. The plan is [records/folder-sizes.md](../records/folder-sizes.md).
- **Folder sizes the app measures by itself give way** (2026-11-16). An automatic walk (the Info panel's or the Info Row's) of a window not in front is stopped for any size asked for and for the front window's automatic one, and waits again while its window still describes that folder; a tab behind another tab, or a minimized window, drops its automatic walk, and a request whose view moved on or closed leaves the queue. A window you aren't looking at shouldn't make the one you are wait minutes.
- **Folder sizes changed outside the app stay as they were measured** (2026-11-16) until measured again, by the refresh button beside the size or Calculate Size. The app's own writes still adjust or forget them. Forgetting the sizes of folders the watchers see change, or marking them as possibly outdated, was weighed and not taken.
- **Calculate Size measures again, one folder or several** (2026-11-17). With several folders selected it used to measure only those with no size, so on a selection already measured it did nothing, where on one folder it always measured again; the same command now does the same thing. The cost is accepted: a large selection is walked whole each time it is asked for. A folder being measured or waiting is left to finish. The Info panel's Calculate, which shows only while a size is missing, still measures only what is missing; its refresh button measures all again.
- **A folder size waiting for another to finish says "Waiting…"** (2026-11-16), apart from one being measured, so a long wait behind another folder doesn't look like a slow walk; the folders of a Calculate Size on several whose turn hasn't come say so too (2026-11-17; they showed "--"). In the Activity list such a request is one row for all its folders, counting those done, with one Stop for them all. A row "3 more folders" beside the folder being measured, tried first, ended as "No longer waiting" between rows that said "Done", which read oddly.
- **While the Activity list is open no row changes place** (2026-11-17). A row whose item ended stays where it was, dimmed, saying how it ended, with no Stop; what is new goes to the end; only the row of a measurement the app started by itself is taken out, as the Info panel or the Info Row shows its state already. Opened again the list shows only what runs. Rows that moved up as one ended put the next row's Stop under a press aimed at the one that went; ignoring Stop for a moment after a move, tried first, still let the list jump and dropped presses without a word. The list shows six rows and scrolls past that, so a long one is not a tall one. The ring's count has nothing behind it at rest, so it looks the same with one thing running as with several: the owner doesn't want its background to change.
- **A folder size says nothing of folders it has no permission to read**, which count as empty, as in Finder (2026-11-16). Hard links counted each time they are met, and iCloud files not on the Mac, stay counted as they are.
- **New Folder with Selection (⌃⌘N, Finder's key) puts the selected items in a new folder beside them, and one Undo takes it all back** (2026-11-19). It works as Finder's does: the folder takes the next free "untitled folder" name and opens for naming, and one Undo moves the items back out and puts the folder in the Trash, asking first only when something else was put in the folder since. It is for items of the folder on screen only, not search results or the Trash. Each item is a rename into the folder, so nothing goes through the paste review; an item that can't be moved leaves the others in and is told of, and when none could the empty folder is removed again. This differs on purpose from a folder typed in Move To or Extract To, which is a New Folder of its own and undone apart from the move.
- **New File makes a file from a template, with its own date** (2026-11-19). File ▸ New File offers an empty Text File and each file of the Templates folder (`~/Library/Application Support/com.filetrail.native/Templates`); Save as Template copies the selected files there as Copy To copies. What was decided:
  - **Only a template's contents are copied**, so the new file is dated now and takes none of the template's tags, permissions (a script template's copy isn't executable) or quarantine mark. The owner chose to leave it so (2026-11-20), since a copy that can't run can't get past Gatekeeper.
  - **Only plain files are listed**: no folders or packages, nothing hidden. Save as Template is offered for files only, as New File lists files only.
  - **Save as Template is not offered for a file whose name starts with a dot** (2026-11-20). It took `.gitignore`, said "Copied to Templates", and New File never listed it. The owner chose to keep "nothing hidden" in New File's list and dim Save as Template over listing hidden templates.
  - The new file takes the template's name, numbered when taken, and opens for naming; Undo moves it to the Trash, as Paste as File's. New Text File has no key until one is set in Settings.
- **Replace Older brings a copy up to date, and is offered only where dates can be trusted** (2026-11-19). A "For all conflicts" answer for copies and moves: folders merge, and a file replaces the one there only when its modification date is later by more than the disks can blur; every other file is left as it is. Copies keep their dates, so running it again replaces nothing. What was decided:
  - **The tolerance is the coarsest of the disks involved**: APFS 1 ms, exFAT 10 ms (measured), HFS+ 1 s, SMB shares 2 s.
  - **It isn't offered at all on FAT**, which keeps local time with no time zone, so a daylight-saving change or a trip shifts every date by an hour, **nor on any other disk** (NFS, AFP, WebDAV, NTFS, unknown). The owner decided the button is simply absent, and Help says why.
  - **Packages aren't compared** (2026-11-20). A package's date is its outer folder's, which stays as it was when something deeper inside changes, so a virtual machine, a `.sparsebundle` or a Photos library changed in place looked "Not newer" and was left stale, and one newer outside could replace newer things inside. The owner chose to leave such a package as it is and say so ("Package · not compared"); a move leaves the source package where it was. Replace can still be chosen on its row.
  - **A clash of kinds is left as well**, and the result says Replace Older left it, as what Add Missing leaves says Add Missing left it (2026-11-20): both said "you chose Skip", which the person hadn't. A Skip the person did choose still says so.
  - It decides per file, inside merged folders too, and goes through Replace's own checks; a choice made for one row wins. As with Add Missing, what is replaced inside merged folders can't be undone.
- **Each item on the clipboard keeps what it was put there for, and the clipboard can be added to** (2026-11-20; how it was built is in [records/clipboard-shelf.md](../records/clipboard-shelf.md)). ⌘C and ⌘X replace what is there, as before; Add to Copied Items (⌃⌘C) and Add to Cut Items (⌃⌘X) add the selection with that intent, so files are gathered from several folders and pasted together. ⌘V copies the copied ones and moves the cut ones in one paste, with one review, one progress card and one Undo. Weighed and not taken: one intent for the whole list, which an Add of the other kind switched for every item (it changed items added earlier without being asked); Finder's way alone, with Cut dimmed for files (it took ⌘X from the people who use it, and nothing on screen said what would move); and asking at each paste of a mixed list (it asks where each item already says). What else was decided:
  - **Move Items Here (⌥⌘V) moves them all whatever their mark.** It is Finder's key and Finder's meaning, so ⌘C and then ⌥⌘V moves, as in Finder; on a clipboard of cut items it does what ⌘V does, and stays on so the habit never beeps. It never means "the other way": there is no key that copies everything.
  - **Nothing has to be remembered.** Paste's second line says what it will do ("Moves 4, copies 3"), the clipboard list is split by intent, Cut above Copied, and the toolbar button shows both counts.
  - **One file has one intent**: put on again with the other, it switches, and is never listed twice.
  - **Each cut item follows its own rule.** One renamed or moved in File Trail is followed; one put in the Trash, deleted or moved outside the app leaves the clipboard alone. A toast names it where nothing else says it went: its disk was ejected, it was dragged to another app, or Empty Trash erased it ("“notes.txt” is no longer on the clipboard", or how many cut items for several). Move to Trash and Delete show a toast of their own that names the item, which is the word for those, and a copied item leaves without one. Changed on 2026-11-20: this entry said every such item left "with a toast naming it"; none was shown anywhere, and one beside the Trash's own toast would say the same thing twice. This replaces the rule that any change to one cut item cancelled the whole cut, which made a list gathered over minutes vanish when one file was renamed.
  - **A paste that moves anything uses the list up** (2026-11-20): what it pasted, copied items too, comes off, and only what it didn't get to stays, to be tried again. The items gathered are one job, and copies left behind would make a later ⌘V paste part of it. The owner chose this over keeping the copies; a list of copied items only is left as it is, to be pasted again, as after Finder's Copy.
  - **A folder and an item inside it are never both on the list**: adding the folder takes the item off, and adding an item inside a listed folder is refused, naming the folder.
  - **A list built with Add and replaced by ⌘C or ⌘X can be put back once**, from the toast that says so and then the clipboard list's footer, until the next Copy or Cut or a quit. It is in neither the menus nor the palette, as no one looks for it once the moment has passed; a list never added to is replaced without it.
  - **Two items of one name are settled when the second is put on, never at the paste**: Keep Both (the one added is pasted under a name of its own), Use This One or Don't Add, asked once for all an Add brings. Names are compared as most Macs' disks compare them: whatever their case, however an accented letter is stored. Conflicts with what is already in the folder pasted into stay in the paste's review.
  - **An item switched in the open list stays on the row it is on**, with its new mark and the parts' counts as ⌘V will run, and the list is in its parts again the next time it opens (2026-11-20, from a review): the item went to the other part as it was clicked, another came under the pointer, and a second click, to switch it back, switched that one.
  - Show Clipboard gets ⌃⌘V, beside the Adds' keys; it had none.
- **Paste as File saves the image or text on the system's clipboard as a new file**, with ⇧⌘V, in the folder on screen, named "Pasted Image.png" or "Pasted Text.txt" and opened for naming; Undo moves it to the Trash. It is the only command that reads the system's clipboard: ⌘V still pastes only what was copied in File Trail (see "File Copy, Cut and Paste use the app's own clipboard"). What was decided:
  - **Not ⌥⌘V**, which is Finder's Move Item Here: pressed after ⌘C out of that habit, it would write whatever the system's clipboard held.
  - **Plain text wins over an image**, as a copy from a document or a spreadsheet carries a picture of it too, unless the text is only an address (a browser's Copy Image) or only spaces and line breaks.
  - **An image keeps the bytes it was copied as** (PNG, JPEG, HEIC, GIF), so nothing is encoded again; one copied only as TIFF is written as PNG. Of several formats the first in the clipboard's order is taken, as the app that copied it lists its own first. Text is written as plain UTF-8, styled text included.
  - **No settings.** A choice of image format was turned down, as forcing PNG makes photos several times larger and forcing JPEG blurs screenshots' text and drops transparency.
  - **Nothing is asked first**, as the file is new, replaces nothing and can be undone, except before writing what a password manager marked as private (`org.nspasteboard.ConcealedType`): Cancel is the default there.
  - **Files copied in another app are refused** with a toast, never written as their icon or name.
- **Copy Contents puts the image or text of one file on the system's clipboard**, to paste in another app, with ⇧⌘C. It leaves the app's own clipboard alone: ⌘C, ⌘X and ⌘V still copy and paste files. It only reads, so it runs in search results, in the Trash and while a file operation runs. One file only; no settings. What was decided:
  - **⇧⌘C pairs with Paste as File's ⇧⌘V.** In Finder it opens Go ▸ Computer, and pressed out of that habit here it only replaces the clipboard.
  - **The menus name what it would copy by the file's kind** ("Copy Image", "Copy Text"). A name that doesn't say (no extension, an unknown kind, or `.key`, `.crt` and `.cer`, which name either) shows "Copy Contents" and the file is read for an image, then for text. A kind that is neither is left out of the right-click menu and the Info panel.
  - **An image goes on as its own bytes**, with a PNG copy for any format but PNG and JPEG, as many apps read only PNG. The file's address never goes on, so other apps paste the picture, not the file.
  - **Text is read as UTF-8, or UTF-16 with its byte-order mark**, and anything else is refused rather than guessed. SVG is copied as its markup; an RTF file goes on with its styles too. A link copies what it points to.
  - **Up to 10 MB of text** (more holds up most text fields) **and 100 MB of image.**
  - **Before copying a name that usually holds a password or a key** (`.env`, `.netrc`, `.npmrc`, `*.pem`, `*.key`, private SSH keys and the like, but not their `.pub`), it asks, Cancel the default, and marks the text as private (`org.nspasteboard.ConcealedType`) so clipboard history apps leave it out. A link is asked about for its own name or for the name of what it points to; a name whose extension says image never is.
- **Share… shows the system's share popover for the selected items, as Finder's does.** It is `NSSharingServicePicker`, with everything in it as macOS chooses for the items, so nothing is listed, kept up to date or filtered by the app. A submenu listing the services in the right-click menu, as Finder showed before macOS 13, would need `NSSharingService.sharingServices(forItems:)`, which is deprecated. It only reads, so it runs in search results and while a file operation runs. Not for items in the Trash, which are only taken out or deleted for good, nor from the right-click menus of the folder tree, the favorites or the list's background, as in Finder. The Info panel shares the item it shows, a folder included, and names what its button acts on. No key until one is set in Settings.
- **Convert Images makes new image files from the selected ones, in another format or at another size.** A sheet chooses the format (JPEG, HEIC, PNG, TIFF, AVIF), the quality, the size, and whether to keep the metadata, with removing the location apart; it runs as a file operation. What was decided:
  - **A selection is never converted in part.** It is offered only when every selected item is an image the system can read (not SVG or PDF). The kind is judged by the name, so the menus stay instant; a file that can't be read once converting starts is listed with the failures.
  - **Nothing is replaced.** Each new file goes beside its original under the same name with the new extension, numbered when taken; the originals are never touched or offered to the Trash, and one Undo moves the new files to the Trash. A choice of where the files go (the other pane, any folder) was turned down for now.
  - **No image is ever made larger, in its width or its height**: enlarging can't add detail (ImageIO only shrinks, and Lanczos through Core Image makes a picture larger but soft). So a size above an image's own is grayed or becomes the image's, with a note; of several images, those already inside a Fit Within or a proportional box keep their size and are converted only; and an exact size that any of them is smaller than grays Convert, as converting only the others would be a partial conversion.
  - **Proportional, a custom size is a box each image fits inside in its own shape**, as one height can't suit images of different shapes. Not proportional, every image becomes exactly that size, and the sheet warns when the images don't all have the same shape. A picture comes out exactly the size worked out for it, never a pixel more.
  - **Without the metadata, none of it is written in any format**: not the camera's, the location, the caption data, a PNG's text nor the XMP, only what the picture needs to show as it did (its orientation and color profile). With it, a resized image keeps all that one at its size keeps.
  - **Removing the location takes it out everywhere**: the GPS position and the place names, from the caption data and the XMP alike, with the places only the XMP names and a position a camera wrote under a name of its own (any XMP field outside EXIF's whose name starts with "gps" or holds "latitude" or "longitude").
  - **What the picture is stays**: the color profile, CMYK or gray, the 16-bit depth for PNG and TIFF, and an HDR gain map for HEIC, JPEG and AVIF. JPEG has no transparency, so a transparent image gets a white background, and an animation or a file of several pages gives its first frame; the sheet says each.
  - **Converting to the same format at Actual Size is allowed**, for another quality or without the metadata.
  - **Only the system's ImageIO, with no library added**: it reads WebP and JPEG XL but writes neither, and WebP through Google's libwebp was put off.
  - Stop pressed while a picture is being encoded writes nothing of it. The sheet remembers the last choices. No shortcut until one is set in Settings.
