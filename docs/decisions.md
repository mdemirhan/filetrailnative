# Decisions

The owner's decisions about how File Trail behaves and how its code is kept, each with its reason. A change that goes against one of them needs the owner's yes first. Open issues are in [known-issues.md](known-issues.md), background work in [battery.md](battery.md).

## Decisions

- **The minimum macOS is 26.** There are no fallbacks for macOS 14 or 15, and the Liquid Glass look is the only one built.
- **Matching the earlier app pixel for pixel is not a goal.** Prefer the system's controls, symbols and look. Code, tests and goldens that existed only to match the earlier app's stylesheet or layout are gone.
- **The system's look.** Tabs and toolbars use Liquid Glass. Commands use SF Symbols, Finder's where Finder has the command. Sheets, the Info panel and Settings use the system's checkboxes, pop-up buttons, switches, number fields and tables.
- **Font sizes and row heights are the app's own, not Finder's**: sidebar 14 pt, icon labels 13, list 14, path bar 12. From Finder the app takes the Favorites and Locations icons as system symbols, the Locations icon color, the unfocused selected fill and the toolbar's sizes. Favorites icons use the app's accent, not the system's, and the search field keeps its own 200 pt width rather than Finder's.
- **Dark mode uses Finder's colors.** The content's background is the system's content material, so it takes the desktop's tint as Finder's does. The path bar is 3.3% white lighter and the sidebar's gray selection is 13.5% white, both measured from Finder. Light mode is unchanged.
- **Glass goes on brief surfaces only.** Toasts, the progress card, plain alerts (a title, a message and buttons) and the filter pill are glass, and keep their edge and shadow so they read over a white pane. Go To and Move To, the paste review, the Rename sheet, the path bar's suggestion list, and alerts with a list or a field stay opaque. The system's own sheet is opaque and its alert is glass, and glass behind lists and fields lets colorful content smear behind the text.
- **The Info panel is a plain split item**, not the system's inspector item. The toolbar lays its material over plain items only; as an inspector the panel's own color showed through the toolbar in dark mode.
- **File Copy, Cut and Paste use the app's own clipboard**, the one the toolbar's clipboard button lists, not the system's. What this means for people is in known-issues.md. Copy Path puts text on the system's clipboard, and Copy Contents a file's image or text.
- **Batch rename keeps JavaScript regular-expression rules, for now.** `JSRegExp.swift` stays as it is. Moving to `NSRegularExpression` would remove about 530 lines, but it would change what `\d`, `\w`, `\s` and `\b` match (ASCII only today, Unicode in ICU), how `ß` and ligatures fold, which syntax is accepted, and the wording of pattern errors. `expandReplacement` (`$1`, `$&`, `$<name>`) stays either way. Revisit later.
- **The search-result highlight uses `NSRegularExpression` for Regex searches.** The rule above covers batch rename only, where the pattern decides what is renamed. The search itself is done by `fd` with Rust's regex, so JavaScript's rules were never what people got there. Plain Text is marked by the app's own matcher (see "Typing finds names by their letters in order").
- **VoiceOver is not a supported target.** Don't add accessibility work; the VoiceOver-only code is gone. Accessibility identifiers and `accessibilityPerformPress()` stay, as the tests press things through them.
- **There is no import or upgrade path from the earlier app.** The earliest release of this app is v0.8.0, and its bundle id is `com.filetrail.native`. Nothing reads files only the earlier app wrote.
- **A window holds at most 25 tabs.**

## Answers

### How the app behaves

- **Names sort one way everywhere, in the user's language, with numbers in order.** One order (ICU's collator for the user's locale, numeric, ignoring case and accents) serves the folder listing, the tree, path suggestions, search results, Open With and volumes, so `file2` comes before `file10` in search results as in a folder, and a Swedish or Turkish user gets their alphabet's order, as in Finder. For an English user only search results changed. Kind labels and extensions compare as words, digit by digit. The locale is read once at launch. Without the system's collator, names compare as text through Foundation; no table of our own is kept for that case, as it would happen only if macOS dropped `libicucore` for everyone at once.
- **Names the language holds equal come in a fixed order.** `a.ts` and `A.ts`, `Résumé.pdf` and `résumé.pdf`, `file1` and `file01` compare equal in the user's language; they are then ordered by their text, byte by byte (`NameOrder.compareText`), in folders, the tree and search results, whatever order the disk gave them. A descending sort reverses it with the rest. `listing-sort.json` and `search-sort.json` were edited by hand to match, each case checked to differ only by tied names.
- **The startup disk is shown by its real name**, as other disks already were, so a renamed startup disk is no longer called "Macintosh HD". The name is read at launch and on every rename, off the main thread, and open windows follow; the Go menu's item follows it too. Help and the startup disk's row in Settings' Shortcuts keep "Macintosh HD": they name a command, as Go ▸ Home does, and the Shortcuts label also feeds Help's golden.
- **Listings and naming use one list of 37 package extensions.** `.rtfd`, `.xcworkspace`, `.photoslibrary`, `.pkg`, `.sparsebundle`, `.key` and the rest show as one item, not a folder, and carry the system's kind ("Keynote Presentation"). Before, listings knew 10 and called the others folders.
- **Accents match one way, however a name is stored.** Wherever a name is matched against what is typed (the list filter, the search results' filter, Plain Text search, the sidebar's type-to-select and Go To), a plain letter finds the letter with or without an accent ("e" finds e, é, è, ê and ë) and a letter typed with its accent finds only that letter, whether the disk keeps it composed or decomposed. Only Latin, Greek and Cyrillic letters lose their accents; a letter that isn't an accent on another (ø, ł, ı) stays its own. Case folds as Unicode folds it where that gives one letter ("ſ" is "s"), "ß" stays "ß". One matcher (`NameMatcher`) holds the rule. A stored name is never changed, and marks fall on the name as stored. Everywhere else paths compare byte for byte (see "Must stay").
- **Typing finds names by their letters in order.** In a folder, a name is kept when it has the letters typed in that order (Fuzzy), with no rule about where words start; Contains keeps the letters side by side. Fuzzy is the default. Each filter keeps its own mode: it starts in the one Settings → Browsing ("Typing filters by") gives, and the chip in its pill switches it and makes the new mode the default for the filters to come. A default changed elsewhere (Settings, another filter's chip) leaves filters already typed as they are, and search results brought back by Back, Forward or Show Last Search Results come back with their filter's text, mode, selection and scroll. Changing the setting back when results return was turned down: it is one setting for every window, so other filters would change with it and the choice just made would be undone. Over search results the name follows the same setting and the folder a result is in is always matched as Contains, as letters scattered over a path would match nearly every result. The letters matched are marked; over search results a filter's marks replace the search's while it is typed. The selection goes to the first name starting with the text, then the first containing it, then the name the letters fit best. A filter that only grew looks only through what it kept.
- **Plain Text search finds what the filters find.** fd gets a regular expression that ignores case and finds every accented and decomposed form of each plain letter (`PlainTextPattern`), for every Plain Text query, digits included: measured on a home folder of 738,221 items, it costs fd no more time than `--fixed-strings`. The app's matcher then judges each result before it counts, so a search and a filter typed over the same names agree. Plain Text ignores case always; Glob and Regex keep fd's smart case and compare names as stored. There is no fuzzy search through fd: letters in order over a disk find tens of thousands of names and would need a best-match order and a limit of their own.
- **Search stops at 50,000 results.** Fixed, with no setting. A keystroke of the filter over 50,000 results took about 18 ms on an M4 Max once names were compared byte by byte or folded once.
- **Paste as File saves the image or text on the system's clipboard as a new file**, with ⇧⌘V (changeable in Settings) from Edit ▸ Paste as File and the menu of the folder's empty space. It is the only command that reads the system's clipboard (Copy Contents is the one that writes a file's image or text to it): ⌘V still pastes only what was copied in File Trail (see "File Copy, Cut and Paste use the app's own clipboard"). Not ⌥⌘V, which is Finder's Move Item Here: pressed after ⌘C out of that habit, it would write whatever the system's clipboard held. The file goes into the folder on screen, named "Pasted Image.png" or "Pasted Text.txt" (numbered when taken), and is renamed in its row as New Folder's is; Undo moves it to the Trash. The menus name what it would write ("Paste Image as File", "Paste Text as File"). Plain text wins over an image, as a copy from a document or a spreadsheet carries a picture of it too, unless the text is only an address (a browser's Copy Image). An image keeps the bytes it was copied as (PNG, JPEG, HEIC, GIF), so nothing is encoded again; one copied only as TIFF is written as PNG. Of several formats, the first in the clipboard's order is taken, as the app that copied it lists its own first, and TIFF only when there is no other: a HEIC copied with a PNG beside it is saved as the HEIC. Text is written as plain UTF-8 `.txt`, styled text included. Files copied in another app are refused with a toast, never written as their icon or name. Nothing is asked first, as the file is new, replaces nothing and can be undone, except before writing what a password manager marked as private (`org.nspasteboard.ConcealedType`): Cancel is the default there. No settings: a choice of image format was turned down, as forcing PNG makes photos several times larger and forcing JPEG blurs screenshots' text and drops transparency.
- **Copy Contents puts the image or text of one file on the system's clipboard**, to paste in another app, with ⇧⌘C (changeable in Settings) from Edit ▸ Copy Contents, the file's right-click menu and the Info panel's quick actions. ⇧⌘C pairs with Paste as File's ⇧⌘V; in Finder it opens Go ▸ Computer, and pressed out of that habit here it only replaces the clipboard. It leaves the app's own clipboard alone: ⌘C, ⌘X and ⌘V still copy and paste files. The menus name what it would copy by the file's kind ("Copy Image", "Copy Text"); a name that doesn't say (no extension, a kind the system doesn't know) shows "Copy Contents" and the file is read for an image, then for text. A kind that is neither (a PDF, an archive) is left out of the right-click menu and the Info panel; from the menu bar it says so in a toast. One file only. It only reads, so it runs in search results, in the Trash and while a file operation runs. An image goes on as its own bytes under its own type, with a PNG copy, turned as its orientation says, for any format but PNG and JPEG, as many apps read only PNG; the file's address never goes on, so other apps paste the picture, not the file. Text is read as UTF-8, or UTF-16 with its byte-order mark, and anything else (a zero byte, another encoding) is refused rather than guessed; an RTF file goes on with its styles too. SVG is copied as its markup, `.ts` and other code the system calls something else as text. Up to 10 MB of text (more holds up most text fields) and 100 MB of image. A link copies what it points to. A copy says so in a toast, and "Copying…" shows when a slow disk holds it up past half a second; the copy asked for last is the one that lands. Before copying a name that usually holds a password or a key (`.env`, `.env.*`, `*.pem`, `*.key`, private SSH keys but not their `.pub`), it asks, Cancel the default, and marks the text as private (`org.nspasteboard.ConcealedType`) so clipboard history apps leave it out. No settings.
- **Quick Look is ⌘Y and Space**, as in Finder. ⌘Y comes first, so the File menu and Help show it (the menu can't show Space) and the toolbar's tooltip names it.
- **Space and the filter.** Space never starts a filter. While one is typed, Space types a space for a second after each key and then is Quick Look; taken off Quick Look in Settings, it always types a space. The arrows always move the selection; the filter has no caret. ⌥⌫ takes the filter's last word back.
- **List view's columns keep the widths they were given.** A pane narrower than the columns (a narrow window, the Info panel open) scrolls sideways; no column shrinks or hides to fit, and Name is never squeezed. A column dragged past the pane's edge scrolls the list so its divider stays in view. Widths change only when someone drags, steps or double-clicks a divider, so what is set is what shows.
- **The Icons view's icon size and the Compact List's column width are set with one slider in the status bar**, and with View ▸ Make Bigger, Make Smaller and Default Size (⌘+, ⌘- and ⌘0, changeable in Settings; ⌘= is ⌘+'s other key, as most keyboards type + with Shift): icons from 32 to 128 pt in steps of 8, columns from 160 to 600 pt, the commands going to the next whole 40, each kept for each density in every window. The List has none. The items are named for the view ("Make Icons Bigger", "Make Columns Wider") and are dimmed in the List and at the ends of the range. While the slider moves, or after one of the commands, the size shows in points in place of the status text, and fades once it stops. Dragging the gaps between columns was tried and dropped: nothing on screen shows the gaps can be dragged. Icons larger than 64 pt ask Quick Look for 256-pixel previews instead of 128.
- **A click on a sidebar row opens its folder at once.** Nothing waits to see whether a second click follows; the second click of a double-click only opens or closes the folder's branch in the tree. With single-click expand on, the first click already does both, and the second does nothing more. A click on a path bar segment still waits 250 ms, as a double-click there edits the path.
- **File ▸ Remove from Favorites is offered for a Trash favorite**, as the context menu is.
- **A full disk ends a paste.** The first "no space" error stops the run, the rest is "Not started", and a partly copied folder is not put in place. There is no free-space check before a paste starts, for now: that is a feature of its own.
- **A file moved to another disk goes even if the disk refused an extended attribute.** A refused attribute is skipped on purpose (most files carry `com.apple.provenance`, and FAT and exFAT refuse many); only a resource fork that can't be written fails the copy.
- **The journal entry that guards a moved item's only copy is flushed to disk.** Other journal entries aren't, for speed; this one is written once per Replace.
- **A folder moved to another disk keeps its journal entry until the originals are gone.** After a crash in between, recovery says what was left of the original and where.
- **Progress counts are taken back when a Replace is undone or asked again**, so the count done never passes the total.
- **A conflict question takes one answer.** If the answer can't be sent, the question stays, its buttons disabled, and Escape still dismisses it.
- **A Replace row in the paste review says what goes to the Trash**, as its footer does, not "Deletes".
- **A tab dropped into a window that already has 25 goes back out** into a window of its own, with the tab-limit notice. The session save still cuts at 25, as the limit doesn't hold everywhere: a folder opened with the app at launch is added as a tab to a restored window even when it has 25, and that stays as it is.
- **Back doesn't follow a folder renamed since it was visited, and Quick Look does nothing of its own when the window's folder changes.** Neither was wanted, and the unwired code for them went.
- **`constructor` and `__proto__` are unknown modifier names** in a shortcut, like any other unknown name.
- **With hidden files shown, Quick Look's button and the hidden-files button both show an eye.** Kept as is.
- **Settings keeps its own row and card layout.** Its controls are the system's, but the page layout is not a control, and a dozen layout tests pin its frames, so `SettingsMetrics` keeps its layout constants.
- **A copy is checked for its source's whole resource fork.** copyfile was once seen to report success with no fork at all on a full disk, its status callback told nothing; why was not found (16 full runs didn't bring it back). Whatever the cause, a copy that reports success with less of the fork than its source fails (`ft_check_resource_fork`): with ENOSPC when the destination's disk hasn't the room for the fork, EIO otherwise. The caller removes it as any failed copy.
- **What a later try of leftover work finds is told as at start.** A move found in place, a rename put back, a folder put in place: shown under "Work was cut short when File Trail last stopped", before the items now in place, in a dialog of their own. Each message is told once, counting what the start already said, so an entry whose record can't be removed doesn't repeat itself every minute.
- **A folder-size walk that finds a sub-folder replaced since it was listed** (now a file or a link), **or gone along with the folder it was listed in** (a folder above it was renamed or removed), fails as incomplete, as an unreadable one does: what was counted is no longer that folder's size. A sub-folder removed from a folder still in its place is left out, as it holds nothing now; failing there made `~` or `~/Library`, where caches are deleted all the time, fail to measure with only the Calculate Size button to show for it. What this leaves: a sub-folder renamed in place before the walk reached it is left out too, and its size with it.
- **The folders drawn by the system are the real special folders, by path:** the startup disk's `/Applications`, `/Developer`, `/Library`, `/System` and `/Users`, and the home folder's Applications, Desktop, Documents, Downloads, Library, Movies, Music, Pictures and Public. A folder of one of these names elsewhere is an ordinary folder, tag color and all.
- **A size step and the selection.** A new icon size or column width keeps the item at the top left of the view (the Icons view) or the column at its left (the Compact List) in place. The selection's lead stays in view if it was in view just before the step; one out of view is left there, and later layouts don't bring it back until it is shown again.
- **A folder opened afresh in the List starts at its top and its left**, an empty one too; Back and Forward put back where it was scrolled. A rename with Name scrolled out of view scrolls back to the left first.
- **⌘⇧= is ⌘+** when a key is recorded or compared in Settings → Shortcuts, as most keyboards type + with Shift; not with ⌥, which types another character.
- **An item opened from another app waits for the items given before it for 3 seconds at most.** One whose disk doesn't answer then lets the next go, and opens itself once its disk answers.
- **A regular expression gets 5 ms of the main thread per name while search results are marked.** One that takes longer stops marking any more names for that search; the search itself is fd's and goes on.
- **Settings lists act on no row while none is selected**: ⌫, Return and Space do nothing, and an arrow selects the first row.
- **A tab can show two panes side by side.** Each pane has its own folder, history, view, order, Hidden Files, Folders First, filter, search and selection; the toolbar, the tree, the Info panel and the commands follow the active pane, which has the blue selection, a short accent line along its top and its path in full color. View ▸ Two Panes (⌘\\) opens the second pane where it was last closed in the tab, or on the active pane's folder, and closes the pane that isn't active. Tab walks the tree, the left pane and the right pane in that order (⇧Tab back; a hidden tree is left out). Copy and Move to Other Pane are F5 and F6 only, so the menu shows no key for them: ⇧⌘C and ⇧⌘X were dropped, as ⇧⌘X a key away from ⌘X would move files at once. They sit in the Edit menu after Cut, Copy and Paste, as AppKit lets an item with ⇧ take the press of the same key without it, should anyone give them ⇧⌘ keys. When a copy, a move or a drag ends, both panes of the tab are read at once, rather than the one not active waiting for the folder watch, and what arrived is selected in the pane that shows it. The right-click menus have one Other Pane submenu, only while the tab shows two panes: Open, Copy and Move for items, Open for a folder in the tree, and Show This Folder and Go to Its Folder on the list's background; an item that can't run now is dimmed, not hidden, so the submenu keeps its shape. Open in Other Pane is ⌥⌘↓ and Swap Panes ⌘U. The tab keeps one tree for both panes: it follows the active pane, marks the folders both panes show, and a pane switch never moves its root; ⌥-click or ⌥Return opens a folder in the other pane, which stays inactive. Panes are side by side only. A saved tab keeps its second pane, the active pane and the divider in optional fields, so a file from before panes reads as one pane; the divider is kept with each tab. The Two Panes button is in the default toolbar; a toolbar saved before it doesn't get it. New Window and New Tab open with one pane; Duplicate Tab, Reopen Closed Tab, Move Tab to New Window and Merge All Windows keep both. A drag from one pane onto the other's list goes into the folder it shows, on its background as on its folders, search results included, and the pane that takes it becomes active.
- **A filter can be pinned to its pane.** View ▸ Pin Filter, or the pin in the filter pill, pins the filter typed in a folder; the same item, checked while pinned, or the pin again, unpins it, and the text is an ordinary typed filter again, to edit or clear. The pill's ✕ removes the filter, pinned or not. A pinned filter belongs to its pane, not the tab or a folder: it applies to every folder the pane goes to and to its search results until it is unpinned or removed, and the other pane keeps its own or none. While pinned it applies to files only, so folders always show and the pane can still be walked; a typed filter still filters folders too. It is locked: typing selects the first name that starts with what was typed (as the sidebar's type-to-select, a pause starting over, nothing shown), Backspace and ⌥⌫ do nothing, Esc lets go of the letters only, and the chip keeps the mode it was pinned with. Showing or renaming an item it hides (Reveal, Go To a file, a paste) unpins it, and a toast says so. ⌘F does not carry it into the search field. It moves with its pane through Swap Panes, and is carried where a typed filter is: by Duplicate Tab, Move Tab to New Window and Merge All Windows, for the pane whose view the tab keeps. Reopen Closed Tab, New Tab and New Window start without one, and nothing of it is saved when the app quits. Pin Filter has no default key. The pin leans 45°, and the pill stays glass while pinned, though it may stay on screen for a long time. A pin per folder, a second filter typed on top of the pinned one, and saving a pinned filter to the Favorites were each tried in mock-ups and dropped.
- **Previews is the fourth view.** View ▸ as Previews (⌘4) and the fourth segment of the toolbar's view switch show a pane's files as large Quick Look previews in a grid that scrolls down; each pane, and search results, choose it as they choose any view. View ▸ Make Bigger, Make Smaller and Default Size ("Make Previews Bigger"…) and the status bar's slider, with four stops, go between 9, 4, 2 and 1 previews at a time, in 3 by 3, 2 by 2, 2 by 1 and 1 by 1; 4 is the default, kept for each density in every window (`previewCounts`). The places share the pane's width and height exactly, with no padding above or below, so a row at the top shows the shape's previews whole and nothing of the next; the preview size follows the pane, so a pane half as wide shows as many, smaller. A trackpad swipe that ends between rows settles on the next row the way it went once it went a sixth of a row, otherwise back; the arrows move a row at a time. Each picture fills its place in its own proportions, never stretched, with a 6 pt margin and its name right under it, and the selection hugs the picture. Everything else is the Icons view's: selection, keys, drags, rename, every command. Holding ⌥ over a preview magnifies the part under the pointer three times from a full-size picture, the selected previews together, kept only while ⌥ is held. Previews are asked of Quick Look at their place's size in the screen's pixels, in steps of 256, at most the screen's longer side. They are kept apart from the Icons view's (the List and the Compact List show icons only), at most 1 GB or a sixteenth of the Mac's memory when that is less, counted by their pictures' pixels, the least recently used going first; all go when macOS says memory is short. Quick Look keeps its own cache on disk, which the app neither sizes nor clears. A separate triage mode with single-letter keys and an Apply step, kind chips in the filter, a Trash Others on Page command, retake groups, copying an image or its text, renaming from the text in a picture, and live previews (a PDF's pages, a video playing) were each considered and dropped.
- **A window's tabs can be saved by name as a workspace, and opened again.** A workspace is one window: its tabs with their panes (each pane's folder, view and order, the active pane, the divider), the tab in front, the folder tree and the Info panel with their widths, the column widths, and the window's size and whether it was zoomed, not its place on screen. The whole app is not one, as the app already brings back every window at launch. Window ▸ Workspaces has Save Window as Workspace…, the workspaces in their order and Manage Workspaces…; the list is in Settings ▸ Browsing, where workspaces are renamed, removed and put in order. A workspace opens in a new window, placed as New Window places one; with ⌥ the menu item opens it in this window instead, which takes the window's place and size and closes it. What is saved is a copy, and a window is not linked to the workspace it came from: the menu checks none, and there is no Update. A workspace changes only when a window is saved under its name: the name field of Save Window as Workspace… has a button, or ↓, that lists the saved names to choose one, and the line under the title gives the key of the workspace named. The link made the checked item look like the window it came from, though choosing it opens another, and saving over a workspace is rare enough to take a few steps. A workspace always opens as it was saved, in a new window, also while a window opened from it or saved as it is open: that window may have changed since, and bringing it to the front made the key seem not to work. The first five in the list open with ⌃⌘1 to ⌃⌘5, and in this window with ⌃⌥⌘1 to ⌃⌥⌘5; the keys go by the list's order, not by use, so a key never moves to another workspace. They are Workspace 1 to 5 and Workspace 1 to 5 in This Window in Settings ▸ Shortcuts, each changed on its own. macOS swaps a menu item for the one ⌥ shows only when their keys differ by ⌥ alone, so while they do, the item for this window is the one ⌥ shows; a key chosen that doesn't pair with its workspace's shows both items, each with its key. Save has no key, as ⌃⌘S is the folder tree's. A tab whose folder is gone opens the nearest folder above it, as a tab does when its folder goes, and a notice says how many did. Names are unique ignoring case and up to 80 characters; saving under a name that is taken asks before replacing it. At most 50 workspaces are kept. Workspaces are kept with the preferences in `app-state.json`; a file from before them has none, and a window's `workspaceID` from when windows were linked is not read.
- **Back and Forward when a read fails or is overtaken: left open.** Back and Forward move the history's index before the folder is read, and nothing puts it back. Back to a slow folder and then opening another drops the folder you came from; Back to a deleted folder leaves the old folder on screen with the index moved. Restoring the index when a navigation is overtaken breaks two quick Backs (they go to B and then A on [A, B, C], and a restore would put the index back on C). A fix that holds: remember the index of the folder on screen while a move is ahead of it; restore it when a push, a replace or a read in place starts, and when the current navigation fails with the old folder on screen; do nothing when it is overtaken, and leave the index as moved when another Back, Forward or jump starts.

### How the code is kept

- **Work lands on `main` by fast-forward or rebase**, never by a merge commit, and there are no pull requests. A commit message is one plain sentence saying what is now true of the app, with no `Co-Authored-By` trailer.
- **`scripts/release.sh` runs the tests that drive real windows.** A release is run at the keyboard, and these are the only tests of real windows.
- **`scripts/ci.sh --affected` compares with the previous commit, not with `main`:** the last commit's files, uncommitted changes and new files. On a long branch every module differs from `main`, so it ran everything every time. With no commit before HEAD, or nothing changed, everything runs. The format lint follows the same files.
- **Hand checks are made by whoever does the work**, in the built app, driven by a scratch scenario. The owner checks by hand only when asked, and no longer asks for before and after pictures of a control change.
- **Goldens are expected results kept by hand.** Edit them by hand, never regenerate one from the code's own output, and ask the owner before changing or deleting one a task doesn't name. A golden file holds its cases only; the metadata fields nothing read are gone.
- **The stop and crash recordings run through the write engine**, not only against themselves. All of them can; a recording that ever can't is deleted with the tests that only describe it. The shape tests of the recordings stay, each saying what it guards.
- **Tests that need a file that can't be written fail it with EIO**, not with a full disk, as a full disk now ends the paste.
- **The Undo types keep their hand-written `Codable`.** It is the journal's guard on its format.
- **The write engine's callbacks for Undo, caches and progress don't throw**, as nothing in the app throws from them.
- **The app installs its services once at launch, and the tests install theirs.** `ExplorerServices.current` has no fallbacks; the tests got faster without them.
- **Names with the earlier app's vocabulary were renamed only where plainly left over**: `RendererCommand` is `AppCommand`, `InfoLocale.original` is `InfoLocale.appLanguage`, `CSSTextMetrics.swift` is `TextLineMetrics.swift`, and the copy of `JSString.equals` went. `JSString`, `JSText`, `JSRegExp` and `NodePath` keep their names: they name rules the app keeps, and renaming them is large. Others (`sortedJS`, `jsTrimmed`, `isJSWhitespace`, `jsLowercased`, `jsRound`, `nodeText`, `libuvWords`, `menuAccelerator`, `javaScriptNumber`, `PageWindow` and its kin) were not part of the answer and are left. Comments describe the app on its own terms, as `CLAUDE.md` says.
- **The Finder Trash workaround stays as a diff**, with the commit it applies to named in known-issues.md. That keeps the record at no cost.
- **A few benchmarks gate a release; none run in plain CI.** The one there is: the frame times of scrolling (`FrameTimeGUITests`, among the tests that drive real windows), which every release measures: the List, the Icons view and the Compact List, each at its default size and at its largest, on the fixture folder `large/files-3000`, each number the median of three scrolls. `scripts/release.sh` shows them against the last release made on the same Mac model and stops on a clear slowdown of a median or of the share of late frames (the slowest frame is shown and fails nothing); loose ceilings apply as well, and alone with no record from that model. Frame times that can't be read or compared stop the release. The limits, with the numbers measured beside them, are in `scripts/lib/frame-timing-limits.sh`. Anything else wanting speed is guarded by tests that bound CPU time (`CPUTime.measureThread`): no other benchmark tests, budgets or `--bench` modes. The fixture tree `large` holds the two folders the folder-size golden measures and the folder the frame times scroll.
- **Each release keeps its notes in its tag.** The notes are written for people before the release starts and given with `--notes <file>`; the script stops without them. The tag's message is "File Trail X.Y.Z", a blank line and the notes word for word (`--cleanup=verbatim`, so Markdown headings stay), and the draft release's text is the same file. A tag pushed to GitHub is never rewritten for this: notes changed on GitHub after the tag is made aren't in the tag. The releases before 1.0.0 had their notes put in their tags afterwards, and their GitHub releases were deleted; the tags stay.
- **Each release keeps its frame times in the commit it tags.** The release adds a record (the version, the date, the Mac model, macOS and the numbers) to `docs/frame-timings.json` in a commit of its own on the checked commit, holding that file alone, tags that commit, and pushes `main` with the tag at once (`git push --atomic`); a release that stops before the push takes both back. The frame times are shown again once the draft is made. A release run by an agent shows the owner that table, and publishes only with the owner's explicit yes.
- **A test run that matched no test fails**: `scripts/ci.sh --scope` and the release's tests of real windows (`scripts/lib/test-runs.sh`). A release refuses to run with `FILETRAIL_NO_DISK_IMAGES` set.
- **Tools nobody runs are deleted.** `scripts/hands-on-setup.sh`, the `FILETRAIL_TIMING` switch and `tools/acknowledgements` went. The licences the app shows are kept by hand in `Resources/Acknowledgements`. `--snapshot` stays: it draws a window into a PNG without screen-recording permission.

## Left out on purpose

Not done, and not to be done without a plan of its own. Kept so the reasons are not lost and the findings not rediscovered.

- **Batch rename on `NSRegularExpression`.** See "Decisions".
  - The search-result highlight did move to `NSRegularExpression`; batch rename did not.
- **The file clipboard on the system pasteboard.** See "Decisions".
  - known-issues.md now says so for people.
- **Fuzzy search through fd.** See "Plain Text search finds what the filters find".
- **The sidebar filtering as the file list does, or a "contains" fallback to its type-to-select.** The sidebar keeps prefix type-to-select with its reset timer and shows nothing of what was typed, as Finder's does. The tree knows only expanded rows, and a tree filter has to keep parent folders and can hide the current location.
- **The sidebar as a real source-list outline** (about 1,000 lines). A redesign with every sidebar interaction test redone.
- **The in-window dialog framework replaced by `NSAlert` and sheets.** High risk; about 3,800 lines of tests drive it.
  - The cheap part is done: alerts and sheets share one base for their panel, footer, button row and Tab order, and use the system's checkboxes and pop-up buttons.
- **The clipboard popover as an `NSTableView`; the path bar as `NSPathControl`.** Worth doing once the system controls elsewhere show how they sit.
  - Sheets, the Info panel, Settings and the icons are now the system's; these two are still not specified.
- **Menu enablement by `validateMenuItem` instead of pushed state.**
  - The cheap part is done: the menu bar is updated in place, not rebuilt.
- **Drag tracking by AppKit's callbacks** (`draggingEnded`, the system's spring-loading) instead of timers. Needs hand tests of drags from other apps first.
- **One write slot instead of two kept in step by a polling loop, and the early-event buffers.** Sound today; the order of "operation ended" against "next write may start" is delicate.
  - When stalls were measured, the paste's `usleep(50)` loop at its end and the progress hop to the main queue (about 1 µs an event) were left with it.
- **The six in-memory file systems in the tests.** Moving them onto real temporary folders is about 1,900 lines of test changes, with medium confidence.
  - The file-system protocols' members are now all required, so every test double implements them all.
- **Flushing a cross-disk move before deleting the original.** Today the original is deleted after comparing kind and size. Recommended later: one full sync of the destination volume before the originals go. Needs a decision on the cost.
  - The move's journal entry now stays until the originals are gone. Still not flushed: the record of a folder move to another disk, which a power cut could leave naming a folder that isn't the paste's.
  - A folder that replaces another by a move to another disk has the same gap, and a wider one: after a power cut that loses the other disk's last writes, the folder at the destination can still be the one that was to be replaced, and recovery, finding a folder there and the original at its source, says the moved folder is in place. Telling the two apart needs the journal to say when the swap was made, which is a change to its format and to the order of a Replace's writes.
- **Partial files under 32 MB left behind by a crash.** Needs a measured cost of journaling smaller files.
- **File ids of 2^53 or more treated as unknown.** Needs a check on a FAT disk of which ids are really shared.
- **Date and number formats tied to the language, not the region; English words around localized dates.**
  - Names now sort in the user's language; dates and numbers are unchanged.
- **The default accent as the system's accent.**
- **An update mechanism.** There is none; people are not told of new versions.
- **The app log file.** Nothing in the app reads it; keep it if people are asked to send it.
- **The response cache's 3-second lifetime, the hand-written app-state writer, the visited-folders ranking constants, the path bar's 250 ms single-click delay, matching AppKit's private views by class name.**
  - The response cache never merged identical requests in flight: two listings of one folder asked at once both read it. Left as is.
- **Alerts are not clamped to the window's height.**
- **Small helpers that are similar but not identical** (parent path, leaf name, trimming with different whitespace sets, exact path equality, thousands grouping with different locales, key codes, "hold until released" test gates, the review-resolve-execute test harness, three seeded generators in tests). Take one only when a bug fix touches it.
  - The identical copies were merged. These differ and stay apart: the drag rules' volume root (it counts UTF-16 units), the disk-image name trim and the application path trim (different whitespace sets), the counts in Eject and the toolbar (they round above 2^53), the clipboard summary's plural (no grouping), the counts that follow the locale, and `Date.epochMilliseconds`, which rounds in FTFoundation and rounds down in FTFileSystem.
- **Test folder and suite names that no longer match their contents, and duplicate tests of the same behavior.**
- **About 30 "nothing happened after a fixed sleep" checks; the goldens that depend on the machine** (`kind-strings.json`, `folder-size-trees.json`, `search-sort.json`); **tests that depend on installed apps, the system appearance or the keyboard layout.** A larger piece of work with little payoff per test.
- **The size of the screenshots in `docs/screenshots`** (about 8 MB).
- **Settings' rows and cards on `NSGridView` and `NSStackView`.** Settled meanwhile: page layout, not a control, and a dozen layout tests pin exact frames.
- **Caching the write engine's looks at destinations.** Settled meanwhile, by measuring: dropping a look before a file's copy would save about 0.1% of a small file's time, and caching the review's path lookups about 5% of a review of 2,000 conflicts, at the cost of threading a cache through safety checks that must run twice.
- **Moving a restored window back on screen.** Settled meanwhile: AppKit already moves a window whose frame is off every screen onto the main screen when it is shown.

## Must stay

Things that look removable and are not. Don't change them; if a change seems to need it, ask the owner first.

- The coordinator's write slot; hidden-name staging and the journal; the `isStagingName`/`isTemporaryName` checks before recovery touches anything.
- `renamex_np(RENAME_EXCL)` everywhere, with the ask-again loop; `removeEmptyFolder`'s read before `rmdir`.
- Replace's re-check after staging, the counted and lock-scanned permanent delete, and never offering delete-for-good on the startup disk or for an unexplained Trash failure (`Native/TrashItem.swift`).
- The replace-safety checks, made at review and again at run time; `assertNotWrittenByThisPaste`.
- Byte-exact path comparison (`sameText`, `NameKeys.Exact`): Swift's `==` treats NFC and NFD as equal.
- The `copyfile` status callback in `Sources/CFileTrail/copyfile.c`; the large-file tests.
- Undo and Redo as they are; `UndoFuzzTests`, `BatchRenameFuzzTests`.
- `JSRegExp.swift` and `expandReplacement` (batch rename's rules, above); `NodePath`; `CopyPasteNames.detectCaseSensitivity`.
- The `fd` binary, `FdProcess`'s `posix_spawn`, the trailing `"--"` in its arguments, `HiddenFilter`.
- FSEvents for folder watching; `ExplorerWindows.reconcile()`; `WorkspaceSplitView`/`WorkspaceSplitController`; `FileRefusingFieldEditor`; `FirstClickGate`; `SecondInstance`; `RenameDrafts`.
